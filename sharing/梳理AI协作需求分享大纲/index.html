三类票务需求，三种不同的协作方式

01 / 三类场景

先判断：开始做需求时，我们手里已经有什么

已有信息不同，
和AI协作的方法也不同

方向基本明确

我熟悉系统，也知道为什么改、准备怎么改。

我定方向，AI补完整

没有成熟答案

逻辑多、关联深，字段和规则无法一次想全。

用原型和实操推演

已有成熟竞品

有经过真实使用验证的通用流程和业务逻辑。

竞品作底稿，逐步共创
关键不是“要不要用AI”，而是先判断AI应该补全、推演，还是帮助参考和取舍。

场景一｜适用：范围小、改法相对明确

我定方向，AI把需求补完整

我更清楚

为什么改、改哪里

现有系统、问题背景、修改方向和本期边界。

+

AI更适合展开

规则有没有补全

异常分支、提示、按钮状态、局部原型和验收条件。

02 / 场景一

日常迭代

我先把方向和边界说清楚

01为什么做现在有什么问题，要解决谁的什么操作困难
02当前是什么提供现有需求、Wiki、页面截图或原型
03准备怎么改我熟悉系统，直接告诉AI修改方向
04本期边界哪些要改、哪些旧逻辑保留、哪些不在本期
03 / 场景一

步骤2｜补全细节，并总结方法

AI把一个改动，
补成完整需求

展示条件
异常分支
提示文案
按钮状态
是否允许提交
验收标准

方法总结：说明问题与现状 → 明确改法和边界 → AI补规则与异常 → 局部原型 → 验收标准

场景二｜适用：逻辑多、跨模块、没有成熟答案

先让业务在原型里跑起来，
再沉淀完整方案

为什么不先写完整方案

细节多、关联深，单靠脑内推演很难一次列全。

原型承担什么作用

把抽象逻辑变成真实操作，让遗漏和冲突更早出现。

04 / 场景二

定制化复杂大需求

先把方案全想完，
反而更难

“字段还没定，记账逻辑已经跨了八九个页面。”

靠脑内推演，很难一次列全；写完再画页面，往往还要大改。

合作伙伴档案
预付款 / 挂账账户
售票与订单
充值 / 回款 / 退款
资金流水与报表
05 / 场景二

步骤1｜先建立系统上下文

我来圈定范围，
让AI学习现有系统

我明确告诉AI去看哪些板块

例如团队管理、分销管理、售票窗口、订单详情等。范围由我来圈定，避免AI无目标地理解整个系统。

结构框架
业务术语
业务逻辑
板块关联
功能关系
详细规则

目的是让AI建立系统上下文、理解可参考架构；是学习，不是照搬。

步骤2｜先搭业务骨架

先定真实用户操作主线，
不急着列完所有字段

建档→建账户→充值→售票→订单→回款→退款→对账
先知道用户会经过哪些环节；字段、状态和异常，留到对应页面中逐步确认。
06 / 场景二

步骤3｜逐模块制作可操作原型

一个页面一个页面，
把业务跑起来

做一个页面
加入样例数据
自己实际操作
规则写回方案
重新跑通
发现缺口，改原型
→→→ →→→
每页固定确认

谁操作？从哪进？要完成什么？字段够不够？不同状态怎么变？会影响哪些下游页面？

原型不是最后的展示图，而是用来发现需求的业务模拟器。

07 / 场景二

步骤4｜在原型上实操，暴露遗漏细节

不只看页面，
要自己完整操作一遍

举例：做一笔充值
充值弹窗是否成功？
账户余额是否变化？
充值 / 其他收入记录是否生成？
后台资金流水能否查询？
售票窗口报表是否统计？
实操重点检查

输入是否够用、状态是否正确、数据是否流转、关联页面是否同步、结果能否继续查询。

例子说明：一个操作真正跑通，才能确认这条业务链已经闭环。

08 / 场景二

步骤5｜原型、实操和样例数据反推方案调整

原型暴露的变化，
会反向推动方案修改

页面操作发生变化

推动入口、布局、操作顺序和交互方案调整。

字段和数据发生变化

推动数据结构、业务规则和记录内容调整。

状态与判断发生变化

推动主流程、异常分支和提示规则调整。

上下游联动发生变化

推动模块范围、关联关系和验收标准调整。

方法总结：学习现状 → 确定操作主线 → 逐模块做原型 → 加样例实操 → 将验证结果写回方案。

场景三｜适用：复杂大需求，但已有成熟竞品

把竞品变成需求底稿，
再逐步共创自己的方案

竞品能提供什么

经过实际使用验证的通用流程、功能结构和常见规则。

我们仍要决定什么

哪些适合自己的业务，哪些需要调整、删减或重新设计。

09 / 场景三

为什么采用另一条起步路径

复杂度没有降低，
只是不用从零构建业务骨架

共同点

都不可能一次想全

业务链路长、参与角色多、状态与规则相互影响，都需要逐步讨论和验证。

复杂需求的共性
边讨论、边验证、边补全
+

场景三的优势

已有成熟产品可参考

通用流程和行业逻辑已经真实运行过，可以先借来建立完整认知。

竞品是起点和依据
不是照搬的最终答案
10 / 场景三

第一步：先确定怎样沟通

先让AI给采集建议，
再按建议准备竞品资料

1. AI先给建议

根据分析目标，先列出采集方式、所需范围和防遗漏检查清单。

视频还是截图？

视频帮助理解连续操作；截图便于逐字段、逐状态分析和引用。

采集哪些端？

管理端配置与游客端结果必须成对采集，不能只看其中一端。

哪些细节不能漏？

弹窗、展开项、错误提示、空状态、成功结果和修改取消过程。

11 / 场景三

第二步：整理竞品证据

从“一堆截图”变成
可查询、可追溯的资料库

逐图识别与中文改名看到文件名就知道属于哪个端、哪个功能
按模块与流程分类把分散页面串成连续业务过程
记录“这张图证明什么”以后每个功能、字段和结论都有证据可回看
12 / 场景三

第三步：恢复竞品背后的业务

先看懂它为什么这样做，
再讨论我们要不要这样做

01完整用户流程

创建活动 → 配置日期场次 → 游客预约 → 修改取消 → 名单管理。

02前后台映射

管理端每一项配置，会怎样影响游客端展示、限制和结果。

03能力全集

日期、库存、填写项、开放截止、凭证、异常状态等完整能力版图。

04证据与未知项

区分截图已证明、多图推断，以及仍需继续验证的内容。

13 / 场景三

一次真正影响方法的踩坑

资料很多，不等于需求不会漏

当时的做法

看到一张截图就聊一张

想到一个问题就插入讨论

局部页面越来越细

没有统一的推进顺序

→

暴露的问题

完整功能和状态容易遗漏

前后台关系没有串起来

讨论内容重复或跳跃

不知道整体进度和下一步

14 / 场景三工作流

第四步：先把需求讨论变成一个有顺序的项目

先用方案确认清单防止遗漏，
不是马上开始画页面

竞品完整流程→功能版图→我们的范围与总体方案→方案确认清单→按模块逐项确认
先定全局

知道有哪些模块、相互怎样关联，以及哪些内容本期要做。

再按顺序推进

每次只讨论清单中的一个模块，完成后留下明确结论。

随时知道进度

已确认、待确认、需补证据的问题都能看见。

先方案，后原型

方案确认清单与后面的HTML页面制作清单是两件事。

15 / 场景三

第五步：固定每次讨论的确认模板

每个功能都要对着竞品证据，
再做我们自己的判断

竞品对应页面

本模块涉及哪些截图；细到字段时，也展示字段所在页面。

理解设计原因

它解决了什么真实操作问题，前后步骤怎样衔接。

做明确取舍

哪些保留、哪些调整、哪些不做，以及放到我们系统的哪里。

确认完整规则

前后台映射、正常状态、异常状态、空状态和最终结论。

16 / 场景三

第六步：从方案阶段进入原型阶段

先定整体方案，
再另列原型清单逐页制作

前半段

方案确认清单

保证业务模块、逻辑、关联关系和范围不漏。

产出：完整方案
以及清晰的功能结论
→

后半段

HTML原型清单

按真实用户流程确定要做哪些页面，以及制作先后顺序。

产出：可操作页面
以及被验证过的细节
17 / 场景三

最后一步｜原型验证，并总结完整方法

竞品作需求底稿，
逐模块共创自己的方案

AI给采集建议→竞品证据库→还原流程与功能版图→方案清单逐项取舍→确认整体方案→原型清单逐页验证
竞品的作用

提供真实运行过的业务骨架，帮助我们避免从零遗漏通用逻辑。

原型的作用

加入样例并实际操作，验证这些逻辑落到自己的系统后是否真正可用。

结论：参考竞品，但不复刻竞品；完整方案仍由自己的业务判断形成。
总结 / 三套工作流

可以直接复用

最终沉淀成三套工作流

01小需求补全问题与改动明确 → AI补规则、异常、原型和验收
02原型推演按真实操作做页面 → 加样例跑通 → 规则写回方案
03竞品底稿共创还原竞品 → 方案清单逐项取舍 → 整体方案 → 原型清单逐页验证
产品经理负责判断，AI负责展开、连接、模拟和检查。
