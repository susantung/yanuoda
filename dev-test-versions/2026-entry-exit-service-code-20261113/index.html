01 · 开发先看：这件事是什么

阅读方式：开发先看第 01—03 节，了解背景、产品思路与明天交付；开发 AI 必须通读本页全部 14 节，并自行阅读产品交付的资料包原件。第 03 节的完整背景与产品思路也请开发阅读；第 04 节起为查证要求及技术细节，由 AI 结合真实代码落实，开发按需复核。简明交接不替代全文和原始规范。

事情是这样：景区收到省厅赋码接入要求，邮件期限为 11 月 15 日，我们按明天（11 月 14 日）先交付后端推进。实际调用方向是省厅来拉取我们提供的数据。当前售票按票品规则选择证件，境外证件主要手填；明天先不动页面，以完整服务码作为输入跑通后端。

首期执行范围后续页面待讨论现有代码与库结构未核实

明天完成后端全链路：输入完整服务码 → 官方 SDK 解析验签 → 有效性判断与字段映射 → 持久化存储 → 省厅接口查询。测试和生产都提供查询地址；测试记录必须由完整服务码实际解析形成。生产没有真实记录时可正常返回空结果。暂缓的仅是页面入口与现场采集适配，后续页面须先与产品详细商量后定稿。

11 月 14 日 · 首期服务码输入、SDK 解析验签、存储、查询接口及双环境交付。
下一阶段 · 页面采集复用已完成的后端，接页面/设备、游客回填与业务时点。
以后 · 数据使用按原证件大类分析，并利用有来源的国籍、生日等细节。

两项实现原则：存储和游客字段先由开发 AI 查现有代码后决定；解析允许通过 job 异步完成，不要求塞进下单请求，需评估既有校验依赖与实际性能。

02 · 开发先看：明天做什么、交什么

1 / 查证与配置确定输入入口、SDK/证书、字段承接、凭据及景区资料。
2 / 接口与数据输入完整码串，真实解析验签并存储；实现查询鉴权、时间窗及分页。
3 / 双环境交付自测后部署测试和生产，提交真实 URL 与字段约定。
4 / 对方联调明确样例性质与窗口，请省厅真实拉取并留存结果。
首期必须有完成口径
完整服务码输入与解析无需页面，由内部接口/命令/既有调试工具接收完整码串；官方 SDK 实际运行，完成验签、字段映射、码失效检查与结果分类。入口形式由开发按项目决定，不增加未经要求的对外政府接口。 可同步或通过已有 job 异步处理；如采用异步，首期必须连同可靠收码、任务执行、结果落库与查询可见性跑通。
可持久化查询的数据来源原则上尽量完整保存 SDK 解析结果，核心字段可稳定查询；可复用现有模型或新增最小记录存储，不要求绑定测试订单。
查询与鉴权符合本文协议；支持空结果、时间窗、分页、重放、修改与作废后再拉取。
测试数据用完整官方样码经过真实 SDK 处理形成记录，保存可核对的解析与验签结果；隔离、可重复执行、时间窗可查。合成 fixture 只补充分页等测试。
测试和生产接口两者都部署 HTTPS 地址；生产没有真实采集数据时返回成功空数组。
交付材料登记表所需信息、字段取值表、自测结果、请求/响应示例及联调窗口。

首期不依赖：设备采购、游客申领码政策、窗口扫码按钮、票品规则改造、游客表全面扩充、分析报表、完整采集管理后台。SDK 解析验签、有效性判断、持久化及查询均属首期必做；不需要先做售票页面，但也不能只手填 6 项身份字段后称链路完成。

首期用完整服务码实际解析产生的测试记录验证政府拉取链路。测试记录只进入测试环境；生产接口可先空数据。不是把假游客或官方样例混进生产，制造“已实际采集”的结果。

03 · 开发也需看：完整背景与产品思路

开发也需阅读 · AI 须通读全文

为什么现在要做

景区收到赋码工作接入要求。提供的邮件要求在 11 月 15 日前完成接入，并填写《赋码工作接入登记表》；表中分别有测试接口地址和生产接口地址。因此，本次按 11 月 14 日完成首期技术交付推进。该期限来自本次材料，不能推导出现场已强制所有游客出示服务码。

早期沟通被描述为“向公安上传外国人信息”。以新版目录的《第三方扫码数据查询接口对接规范》为本次开发依据，实际技术方向是：我们提供只读接口，由省厅主动拉取扫码记录。本次不开发向公安主动推送资料的任务。官方服务码解析规范与省厅查询协议是链路中的两件事。

当前票务业务是什么样

根据产品说明及截图，每张票配置自己的预订规则，允许录入的证件类型由票品配置决定；售票窗口游客行的证件类型下拉随此变化。目前展示五类：身份证、护照、港澳通行证、外国人永居证、台胞证。身份证已有设备读取，其余主要人工录入。游客信息至少承接姓名、证件类型、证件号、性别。

以上是业务层已知现状。姓名等资料实际放在游客档案、订单游客快照、门票记录还是其他模型，是否已存国籍、生日、扩展 JSON、来源字段，以及各端是否共用一套模型，均需开发 AI 查证。产品未提供实际数据库字段清单。

产品希望怎么分两步

  1. 先完成“拿到完整服务码之后”的全部后端。用内部接口、命令或项目既有调试工具输入码串，真实调用官方 SDK 解析验签、保存结果，再经省厅接口查出；不等待设备、游客领码、前端入口和全部统计改造。
  2. 再解决“现场码怎么来、怎么进入售票页面”。页面或设备取得完整码串后直接调用首期后端能力，衔接当前游客回填及票品规则；不把 SDK 集成留到这一阶段。

产品曾考虑的两种组织方式

思路产品考虑本方案判断
新增“服务码”证件类型先独立放这一类游客，后面单独分析其细节。可以在同一录入下拉中展示“服务码”，但应区分 UI 录入选项与真实证件类型。底层保留服务码来源及原码，解析后获得实际证件类型。规则配置、下拉生成及未解析时的校验方式由开发查证后提出方案；不因共用下拉就永久合并数据维度。明天仍不做页面。
解析后回到原证件大类识别真实证件类型，回填姓名、证件号、性别，并保留服务码带来的国籍、生日等。后续推荐方向：原证件大类＋采集来源＋官方细分类型。映射工作仍要做，但不必把 7 个官方细分都新增到售票下拉。实际模型由开发核实后建议，页面经产品确认。

产品真正关心的是：首期能按时接通；后续能利用额外游客资料做分析；避免现在为了赶工把数据结构做死。并建议尽量完整保留解析资料，但不要求为每一项立即扩列、增加页面或改造全部报表。

04 · 开发 AI：读原件、查现状，再落实施工

给开发及开发 AI：本文表达业务目标、接口合同和产品思路。未读取你们的业务代码与数据库，文中出现的“采集记录”“游客扩展”“关联”等均是逻辑概念，不是已存在的表名、字段名，也不是要求直接照建的数据库设计。先查现状，优先复用，再决定最小改造。
开发及开发 AI 必须自行阅读产品交付的打包文件。本页是产品背景与分析整理，不能代替原始资料。实施前请打开产品给开发的资料包，逐项读取接口规范、SDK 手册及配套 SDK 包、证书、测试样码、更新说明、登记要求及相关沟通附件；核对实际版本与彼此对应关系。不要只看本 HTML，也不要默认产品的分析已替你完成规范核查。开发收到的目录位置可以不同，以实际交付包为准。请回传已读文件及版本清单、冲突/缺失项和对实现的影响；缺少材料时明确指出，不能猜测补齐。

开工先做一次有代码证据的快速核对。能独立推进的接口、鉴权与环境准备同步开展；不要把所有后续页面问题都当作首期阻塞项。

要核对的内容请提供的证据或结论据此决定什么
项目及发布入口实际服务、技术栈、路由/网关、测试与生产部署位置、现有配置方式。复用哪个服务和鉴权组件；实际完整 URL。
游客资料存储链路从窗口提交到持久化、订单/门票读取的代码位置、实际表或模型；是否保存快照。资料应关联到哪一层；避免只改档案而订单仍读旧值。
现有身份字段与扩展能力姓名、类型、号码、性别的实际字段；国籍、生日、原始日期、扩展字段、信息来源是否已具备。已存在则复用；缺少时选择扩展列、扩展模型或独立记录，说明影响。
证件枚举与规则引用实际枚举值、港澳通行证含义、允许类型配置及校验、限购查重、导入导出引用位置。建立官方代码到现有代码的适配；不把中文名称直接当数据库枚举。

隔离与环境配置appId 如何绑定景区/租户；两环境数据与凭据如何隔离；正式单位名和地址在哪里配置。鉴权后只读本景区、本环境数据；生产排除测试样例。
SDK 与证书现有语言是否可直接接官方 SDK；国密依赖、证书管理及真实返回结果。优先复用当前技术栈；首期必须集成并真实运行 SDK。查询协议可并行开发，但不能用跳过 SDK 的 fixture 代替首期完成。
开发 AI 应回传：① 实际代码/模型定位；② 已可复用的能力；③ 首期最小新增与迁移方案；④ 后续关联预留方式；⑤ 对外字段实际取值表；⑥ 部署、自测与省厅联调状态。若现有实现与本文建议不同，只要满足合同和产品边界，应说明取舍，不必为了吻合建议重建模型。

05 · 对外到底要哪些字段，码能解决哪些

新版查询规范固定 15 个记录字段名，其中 12 项必填、3 项可选。这不是“最后只给一个服务码”。完整服务码能够提供其中的 6 项身份字段；另 6 项必填由系统记录、业务配置或事件上下文提供，不能从码串推导。

下表的字段名与必填性来自规范第 7.1 节；取值格式、性别和状态码表属于我方拟定的交付约定，需随接口说明交对接方确认。不能将规范中的示例 certType="01" 当成全国统一且可直接使用的编码。

对外字段必填能否来自服务码建议取值 / 其他来源
recordId是不能从码生成采集/测试记录稳定唯一标识；复用或首次创建后保持不变。
name是码内姓名SDK 字段 zwxm / ywxm；建议中文非空优先，否则英文，取值口径随交付说明。
certType是zjlx建议对外保留 PP/PO 等官方代码；与内部枚举分别适配。
certNo是zjhm证件号按字符串处理，不依据号码猜所有证件资料。
nationality是gj建议保留三位国籍代码；不得由证件大类猜国籍。
gender是xb建议保留官方码值并提交码表；异常不随意转换成男/女。
birthday是csrq建议 YYYYMMDD 原始字符串；未知月日 00 保留，不补造日期。
scanOrgName是码不提供从实际扫码单位配置取得，不能照抄规范旅行社示例。
scanOrgAddress是码不提供实际扫码单位地址，部署前落实。
scanTime是码不提供实际采集时间；测试则如实为测试导入/构造时间并说明性质。
bizItem是码不提供拟用“景区门票购票信息登记”，作为业务取值约定交付。
updateTime是码不提供记录实际最后变更时间，至少秒精度；不能每次查询重新生成。
bizItemCode否码不提供无已分配代码可先 null，随取值表说明，不自行编造正式代码。
dataStatus否码不提供建议 1=有效、2=作废，需交付明确码表。
extra否无需身份扩展建议首期 {}；规范明确允许该字段为 JSON 对象。

保存尽量完整，当前接口只返回约定字段

对外不要求原始服务码、签名、证书序列号、码内流水、版本、码失效日期、签证、入境和停居留资料，也不要求把双语姓名都返回。完整码串仍需交给 SDK 解析验签；不建议为了少几个输出字段自写“只截一部分码”的解析器。

产品建议：SDK 能解析出的资料原则上尽量完整保存，不以当前省厅接口字段为保存上限。包括双语姓名、官方证件细分、国籍、性别、原始出生日期、证件有效期，以及 SDK 实际返回的签证、入境、停居留、码版本/流水、证书序列号、码失效信息等。仅保存当前 6 项身份字段，未来临时增加需求可能无法直接提供，因此首期存储设计就应考虑完整解析结果留存。具体以开发自行核对的 SDK 返回字段为准，未提供的字段保持缺失，不补造。

建议的承接方式：经常查询的核心字段结构化保存；其余资料保存完整的 SDK 解析结果快照（如项目已有扩展模型或 JSON），同时建议保留完整原始码串、实际解析/验签结果及 SDK/解析版本，便于回查、重解析和未来字段提取。完整保存不等于每一项都新建数据库列，也不要求全部塞进原游客表；由开发结合现有结构给出字段清单与存储方案，确有不能保存的内容需说明原因。

存储范围与对外返回范围分开：当前省厅接口仍只按约定字段返回，不因为保存了更多资料就通过 extra 全量输出。以后增加需求时，先从已存解析快照提取；新增报表常用字段再按需索引或扩列，无须重新找游客采集。数据保留期限与访问方式沿用实际项目机制，本建议不表示无限期保存。

码失效日期、验签结果虽不是省厅响应字段，首期后端仍须用于判断输入结果并分类保存；后续页面复用同一结果。不能把“接口不上传”理解为“业务也完全不检查”。

06 · 接口合同与实现注意事项

调用方向：省厅 → 我方 HTTPS POST → 鉴权与参数校验 → 查询持久化记录 → JSON 分页结果。省厅负责定时调用、重试与去重，默认每 5 分钟调用、1 小时时间窗。我们不新增主动推送任务。

请求与签名

HTTPS / TLS 1.2+，请求响应 UTF-8 JSON；30 秒内返回，响应不超过 10 MB。路径可采用 /api/v1/scan-data/query，最终按既有网关规范确定。接口不能跳转到浏览器登录页。

请求头要求
X-App-Id接入标识；登记表呀诺达行是 yanuoda，须核对环境凭据。
X-Timestamp13 位毫秒时间戳，使用请求头原字符串；时钟偏差不超过 5 分钟。
X-Nonce32 位随机字符串。
X-Sign64 字符小写 hex 的 SM3 摘要。
sign = SM3(appId + timestamp + nonce + bodyRawString + secret)

直接拼接，不加分隔符，不替换为 HMAC。bodyRawString 必须是收到的 HTTP 请求体原文，不能 JSON 解析再序列化后验签。请求鉴权的 SM3 与官方服务码的 SM2 数字签名是两套机制。密钥受控配置，不写方案、前端、源码或日志。

  "endTime": "2026-11-14 10:00:00",
  "timeField": "updateTime",
  "pageNo": 1,
  "pageSize": 500
}

参数时间格式固定为北京时间 yyyy-MM-dd HH:mm:ss；结束时间大于开始时间；timeField 固定 updateTime，页码从 1 开始。规范要求支持的 pageSize 上限不小于 200，本方案建议上限 500；超范围按参数错误处理，不静默截断。不自行限制合法补拉的历史时间窗。

查询、分页与更正

  • 按 startTime ≤ updateTime ≤ endTime 闭区间筛选，同时限定凭据绑定的景区及环境。
  • 建议固定排序为更新时间、记录 ID；实际分页必须可重复，不能因初期量小忽略 pageNo。
  • 返回条数达到 pageSize 时，hasNext=true。恰好 500 条也应在下一页返回空数组及 false。
  • 同一记录更正后 recordId 保持不变，updateTime 更新；作废仍能在增量窗口返回。不得删除后让对方无法获知作废。
  • 查询保持只读，不动态刷新业务时间、不临时生成记录 ID。无业务变更的同请求重放，记录及顺序一致；请求追踪 requestId 可按请求生成。
  • 固定排序不能单独保证并发翻页无漏数。研发优先复用已有版本/稳定分页能力，必要时为本次时间窗提供可重读快照，并验证并发场景；具体方案由实际架构决定。

响应结构与错误码

沿用固定信封：code、msg、requestId、total、pageNo、pageSize、hasNext、data。total 规范允许省略，本方案优先准确返回；不新增其他顶层字段。记录的基础字段扁平一层，只有 extra 按规范可为对象。

{
  "code": "0",
  "msg": "success",
  "requestId": "req-example-001",
  "total": 0,
  "pageNo": 1,
  "pageSize": 500,
  "hasNext": false,
  "data": []
}
code（字符串）用途
"0"成功，包括空窗口；data 必须为数组，不能为 null。
"1001"鉴权失败，例如签名不符或时间戳过期。
"1002"参数错误。
"1003"数据库不可用、内部临时故障等；不要伪装为成功空数据。

业务错误使用 HTTP 200 和规范错误码，保留固定信封及空数组；基础设施失败如实记录。nonce 防重放缓存是规范建议，实现时须兼容合法重试，不能破坏只读重放。

07 · 持久化与游客模型：留给开发选择

首期要求的是可查询、可追踪变更、可隔离的数据能力，未要求改造某一张游客表。省厅规范也明确不约束内部库结构。优先检查已有采集记录、事件记录或可扩展游客快照是否能承接；不足时新增最小记录存储。独立采集记录是建议方案，不是已确认存在或必须使用的表。

逻辑信息首期要求后续衔接
对外查询快照12 项必填可稳定查询；可选状态有明确约定。景区配置变化不应静默改写历史快照。真实采集后沿用同一查询协议。
记录身份与变更创建一次，稳定 ID；修改与作废推进更新时间。与游客档案 ID、订单 ID 分开理解，按现有主键规则关联。
数据性质与隔离能区分测试与生产、景区范围；测试有效记录仍是测试，不用“作废”充当测试标记。真实记录只进入正式查询集合，草稿/失败输入不自动对外。
原始码与核验首期实际调用 SDK，原则上完整保存实际解析结果及核验状态、错误结果，建议同时保存原始码串与解析版本；未执行不能视作通过。具体采用扩展模型、JSON 或结构化字段由开发决定。如保留原始快照，应与人工编辑后的售票值分开。
游客及订单关联可为空或暂不建立，首期不创建虚假订单。确认实际事件时点后关联到正确游客/订单快照。
额外游客维度不要求明天全面扩充原游客模型。国籍、生日等现有字段复用；确实缺失再选择加列、扩展表或结构化扩展。
给开发 AI 的选择原则：复用既有模型能满足要求就复用；新增独立记录更稳妥则新增；游客表是否扩充由读取链路和查询需求决定。请给出实际字段映射与必要迁移，而不是把本方案的逻辑名直接转成一套新表。

后续若人工修改从码中取得的姓名等字段，保留原码及其官方原值与本次业务使用值的区别，不继续声称人工修改值等于官方解析值。省厅查询究竟用原始快照还是经确认的更正值，须与产品确定业务口径后实施。

10 · 首期后端与后续页面如何衔接

后端首期必做 / 页面后续讨论

完整目标链路：获取完整服务码 → 后端官方 SDK 验签解析 → 检查码失效 → 映射现有证件类型 → 按票品允许范围处理 → 回填游客 / 保存采集快照 → 进入首期同一查询接口。其中输入、SDK 解析验签、码失效检查、身份字段映射与持久化、查询能力明天完成；票品现场校验、页面回填以及真实售票事件何时对外生效，待与产品确认。首期测试使用明确标识的测试事件，不预设正式售票时点。

服务码是什么，采集和解析如何分工

服务码二维码承载以 EDSC| 开始的完整结构化字符串，包含身份资料和官方数字签名，并非只拿一个短编号再去查询全部个人资料。扫码设备或软件先读取完整码串；后端使用配套官方 SDK 和公钥证书完成验签与字段解析。它与护照照片 OCR、护照机读区识别是不同输入，不能把任意证件号或 OCR 结果当服务码。

因此明天须先实现无页面的完整码串输入能力并跑通解析、验签、存储与查询，再适配售票页面、扫码枪、摄像头等采集方式。设备选型、读码能力、字符编码、回车等传输行为需用真实码与现场设备验证，不在本期预设采购型号，也不要求游客已普遍能出示码。

性能建议：允许异步解析，不要求在下单请求中执行

产品明确允许以 job / 队列任务统一处理解析验签及扩展存储，目标是不影响下单性能。“明天后端全链路做完”指这套能力必须可真实执行并贯通，不表示所有步骤必须在一次下单 HTTP 请求中同步完成。请开发 AI 用真实样码评估解析验签耗时、证书加载与存储开销，优先复用已有任务能力；不要未经测量就认定一定慢，也不为此无依据新增中间件。

可评估的异步链路：输入完整码串 → 可靠保存原码与接收时刻、待处理状态 → 已有 job 解析验签 → 保存身份字段与结果 → 合格记录进入对外查询集合。政府拉取时仅查询已处理完、达到对外条件的持久化数据，不在查询请求里批量跑 SDK。首期如果选择异步实现，要连任务触发、执行和结果存储一起完成，而不是只收码入库。

开发需评估方案需要说明
下单需要哪些字段查清姓名、证件类型/号等必填、实名、限购、查重、票品范围及检票读取的依赖。如果依赖解析结果，不能仅把任务后置后宣称与原逻辑兼容。可评估采集后提前异步预解析、最小必要同步处理或已有资料独立满足校验等方式，具体方案和待解析时能否成交由产品确认。
任务可靠性原码可靠入库后再确认接收；按同一采集记录幂等处理，可重试并发防重复，失败可定位和补跑。状态、重试次数等是否复用已有任务记录由开发决定，不要求新建固定字段。
延迟与增量拉取提出任务频率、预计积压与可接受延迟，不把省厅默认 5 分钟调用当作已批准的处理 SLA。完成解析或更正使记录进入可查询状态时，推进 updateTime，不能只沿用早先收码时间而落在对方已拉完的窗口；scanTime 保留实际采集/接收时间。
未完成或失败待解析、验签失败等不得以缺失必填字段的半成品作为正常记录返回。就绪记录才进入正常集合；后台任务故障可观测，不能把长期无数据当作链路正常。
日期判断与业务状态保存实际采集/接收时间及处理时间。明确有效性判断采用的事件时点，避免仅因 job 延迟便把收码时有效的码判断错误；这与最终售票资格的处理须由产品确认，不修改码内日期。
性能证据说明测试环境、样本量、单码耗时、并发/批处理表现及对下单的影响，再建议同步、异步或混合方案。没有性能测试时只能写待验证，不能承诺“无影响”。

首期后端必须完成的处理

  • 优先采用现有技术栈对应的 Java 或 Python 官方 SDK，不为此无依据新增另一套服务。
  • 按证书序列号选择配套证书；完整码串参与验签，不自行生成官方签名，不将 6 个字段重新拼接冒充原码。
  • SDK 解析验签成功不等于码未过期、人证一致、证件未挂失或订单已成交。核验结果与售票处理结果分开。
  • 已静态核查的 Python SDK 未执行码失效日检查，业务层需要补充。手册与源码返回码存在差异，集成以真实运行核对；Java行为也需实测。
  • 停居留截止日、证件有效期、码失效日期是不同信息。具体哪些情况阻止售票、是否降级人工，先与产品讨论，不自行新增资格限制。
  • SDK可读字段不等于省厅全部要上传；国籍、生日等有实际用途再纳入游客扩展或统计。

查询接口每次拉取直接读取已确认的持久化数据，无须对每一条重新跑 SDK。真实采集启用前必须验证生产证书与实际样码，不能用首期测试导入证明这部分完成。

后续页面方向：同一下拉可以有“服务码”选项

根据本次截图和产品说明，窗口下拉是由票品预订规则的“验证信息”集合生成。产品希望未来在该下拉中与身份证、护照等并列选择“服务码”。视觉上并列，并不要求底层都成为同一类真实证件。选中服务码时进入码串录入分支；保留录入来源和完整码串，解析后另存官方细分与映射后的业务证件类型。异步未完成时真实类型应是待解析/未知，不得临时冒充护照。

不直接要求前端无条件写死追加。请开发 AI 核实规则字段、下拉生成、提交参数、后端校验及历史枚举的整条链路，再评估：① 复用现有规则增加兼容的录入选项，同时在业务模型区分来源；② 保持证件允许范围，另设服务码录入能力配置，再组合为同一可见下拉。实际选项编码、开关和保存位置由现有项目决定，不按本文编造字段；是否展示及对旧票品默认如何处理，须与产品确认。

服务码入口可用，不等于码内所有真实证件都符合该票品规则。解析出 PP 后仍需知道票品是否允许护照。若将这一步也放到下单后，必须先说明原有规则如何执行、何时能执行及失败怎么处理；不能让来源选项自动绕过实名、允许证件、查重或限购校验。该页面方向已记入，但具体交互仍待讨论。

这样组织对分析有什么好处

  • 原证件类型统计可继续使用；护照来源是人工还是服务码，不改变其业务大类。
  • 增加“采集来源”后可先筛选有服务码资料的样本，再按国籍、生日或官方细分类型分析。
  • 人工录入缺少的国籍/生日保持未知，不因为“护照”就猜国籍，也不把无码游客都归为某国。
  • 服务码覆盖中国籍华侨及港澳台居民等，不能把所有服务码游客统计成外国人。CHN 也不能推算省份。
  • 采集事件数、去重游客数、订单游客数、门票张数不同；一人多票或重复采集不能直接按记录条数计游客。

原预订规则对性别、生日、区域等限制的适用条件按现状保留。不能因现在能解析到更多字段，就顺手将原“身份证生效”的限制扩展到全部证件；是否扩展须另行确认。

12 · 后续页面先和产品商量什么

本节是讨论清单，不是前端排期。首批做哪些入口、入口放哪里、回填如何覆盖、何时成为对外记录，都未定稿。先与产品逐项讨论，再出页面方案和原型，确认后开发。
讨论主题需要共同决定当前边界 / 讨论起点
首批入口散客售票是否先做；团队、合作伙伴、取票/线上确认、补录是否首批纳入。这些是业务候选入口，不是已核实菜单路径或全部必做页面。
扫描与目标游客按钮、当前行输入、统一扫描区如何选择；连续扫写到当前行还是新增行。先确认现有读证交互，避免串人和额外操作。
回填与编辑已有姓名/证件号是否覆盖；类型自动切换还是提示；编辑后保留哪些来源标记。同一下拉可增加“服务码”录入分支；规则与来源分开承接，开发查证后提出配置方案。最终真实证件仍需符合票品范围；异步依赖先与产品确认，人工编辑不覆盖原始快照。
无码、失败、过期无服务码是否可人工售票；失败是否保留；到期后如何转人工。目前无已确认强制报码政策，不自动禁止售票，也不标验签成功。
事件时点与对外范围扫码成功、确认游客、订单成功哪个时点形成对外记录；取消/失败交易是否可拉取。这是后续最关键的业务决定，不能默认扫描即上传全部输入。
重复、换人、删行、退票重复扫如何防抖；换人是否另建事件；已对外记录如何更正作废；退票是否影响记录。不按码值永久去重，不把票务退款直接等同扫码记录作废。
预订规则与未带证是否清除未带证标记；是否改变年龄/性别/生日/区域适用范围。默认不变，按现有业务逐项确认。
详情和后台哪些页面展示来源、国籍、生日、细分类型或核验结果；是否需要独立记录管理入口。按实际操作需要决定展示、编辑权限和脱敏范围。
统计与导出具体哪个报表需要国籍/来源；按何种时间算年龄；分母与未知值如何处理。不默认改全部报表，不做全库补造数据。

后续交付应包括：实际页面及菜单清单、端到端流程、逐页字段与校验、异常/取消分支、原型、正式 PRD 和验收点。开发 AI 可以提出实现影响与建议，不能代替产品确认这些业务决定。

13 · 分阶段实施清单与开发 AI 交接要求

阶段开发输出产品/验收关注
