### 开发先读：这次改什么

首期后端已由开发完成，本次补齐散客、团队、长期/临时合作伙伴售票，以及取票、线上票确认中原有游客证件补录的服务码录入；另补齐内导导游开单的散客录入及团队游客带入后编辑。复用证件号输入框接收服务码，后端验签解析通过后，回填真实证件类型、号码、姓名及性别并只读；原码隐藏保留，随游客提交保存。票品资格仍按真实证件判断。

- **入口**：支持下拉选择服务码，也支持普通证件类型下直接扫入 `EDSC|` 开头的码。进入服务码流程后，未成功解析校验不能提交。
- **切换**：服务码资料改选普通类型或重选服务码，先清空当前游客，不弹替换确认；普通人工资料切换类型保持现状。程序回填、挂单恢复不能误触发清空。
- **设备**：原身份证逻辑不改。服务码成功、失败复用现有跳格、连续录入、提示及定位处理。
- **保存**：保留真实身份、采集来源、原码及同次完整解析结果，挂单恢复不丢失。对外订单只排除待付款，其他状态不额外处理。
- **查询兼容**：所有原有游客证件号查询框支持按已保存的完整服务码匹配查询；截图明确 9 页 13 框，范围、查询与新增采集的区别见第 5.2 节。
- **补录入口**：取票、线上票确认的原有游客证件补录弹窗同步接入；补录出现条件不改，复用已有规则，确定保存、取消不生效。见第 5.1 节。
- **内导**：导游开单的散客录入、团队带入后编辑同时接入，来源与原码随游客承接；见第 9 节。
- **团队预约平台**：同步真实证件下拉、保存/暂存、订单提交及后端校验，旅行社端不接服务码、不扩充导入；详见第 2.5 节。
- **后台页面改造**：预订规则“验证信息”复选项同步改名并新增 CF 类型，覆盖新增、编辑和保存回显；见第 2.1 节后的页面改造说明。
- **分类改动**：原“港澳通行证”更名“回乡证”，新增页面选项“回乡证(外籍)”（半角括号）；官方细分名称为“港澳居民来往内地通行证（非中国籍）”，编码 CF。其他原名称不变。两类居住证本次不做。
- **本次不做**：批量导入服务码、新增资料查看/分析页面；不为服务码另加预订规则开关。

- 取票与线上票确认的原有证件补录入口同时接入，不改补录资格、出现时机、权限或原流程条件；本次只扩充已允许补录时的证件与服务码处理。
- 本次完成窗口录入、解析回填、校验、完整资料保存、既有政府查询接口衔接，以及原游客证件查询框的服务码兼容。
- 原有名单导入保持现状，不新增服务码表格导入。服务码成功采集复用身份证设备现有的跳格、连续采集及添加游客链路；跳转目标、增行与票数联动条件须查实际工程，不以独立小样推断。
- 资料详情扩充、导出和分析后续做；现有游客证件查询框的服务码兼容属于本次范围，见第 5.2 节，不新增报表或资料查看页面。
- 挂单恢复须连同姓名、真实证件类型、号码、性别、原始服务码及完整解析结果一起恢复，保持只读和游客对应关系；挂单本身不形成供省厅查询的业务记录。

### 2. 入口、识别及提交的统一判断

本节适用于售票新增游客和第 5.1 节的证件补录。第 5.2 节的既有记录查询独立处理：仅匹配已保存原码，不走本节解析、验签、过期及票品资格判断。

**执行主线：选服务码或识别到 `EDSC|` 开头 → 进入服务码状态 → 完整接收后调用后端 → 验签解析及类型映射通过 → 实名票再校验票品购买规则，非实名票跳过票品规则 → 回填真实类型和号码 → 才可通过该行提交校验。**

| 售票员输入 | 如何判断 | 提交约束 |
| --- | --- | --- |
| 主动选“服务码”后输入任意内容 | 由选择动作明确服务码录入意图，不再猜测所填内容 | 未成功解析校验，不可作为有效游客资料提交 |
| 普通类型下直接输入，以 `EDSC|` 开头 | 仅识别为服务码候选并切入服务码状态，不等于有效 | 无论原来选择何种证件类型，解析不成功都不可按原证件类型提交 |
| 普通类型下输入，不以 `EDSC|` 开头 | 不判断为服务码，沿用当前所选证件的原有录入、校验 | 不新增服务码错误，也不假定原护照录入有严格格式校验 |

`EDSC|` 为产品原始样码中的实际标记；不能写成 DESC，也不能只凭输入 E、ED、EDS、EDSC 就确认是服务码。键盘逐字输入前缀期间可暂缓普通格式报错，但输入结束仍未形成完整标记时应回原证件校验，不报“服务码不完整”。主动选服务码的情况除外。

不能凭长度判断成功或猜“缺两位”。长码须完整接收，不能先按身份证限制截断。普通证件允许长度由研发核查各类型规范与现有实现；如做长度校验，超长明确报错，不静默截断，也不在本方案猜固定上限。自动识别路径须先识别服务码标记，不能被普通证件输入长度限制提前截断。



- 实名票允许服务码支持的任一真实证件类型时，按现有允许范围自动开放服务码入口，不另加服务码开关。仅允许身份证的实名票不开放，直接扫入服务码提示不适用。
- 非实名票允许主动添加游客、选择服务码或直接扫码；不因预订规则未勾选证件就隐藏入口或判定不支持。游客录入非强制，主动录入的服务码仍须通过自身校验。
- 既可先选服务码再输入，也可在当前选择身份证、护照等类型时直接扫入完整服务码并自动识别。
- 普通证件号仍按当前类型及原有方式校验。服务码以设备结束事件、已确认的失焦/提交触发为接收结束依据，不用“等待期间不再输入”或固定长度冒充完整性证明；接收结束后调用后端验签解析，不逐字符请求。实际设备结束符由研发实机核查。
- 实名票映射出的真实证件类型必须符合该票允许范围，来源入口不放宽购票资格；非实名票不校验票品对应购买规则。普通身份证等既有录入逻辑不因本次接入改写。

#### 2.2 实名票与非实名票的校验分流（产品已确认）

| 票品情况 | 是否允许服务码录入 | 票品购买规则 | 服务码自身校验 |
| --- | --- | --- | --- |
| 实名票 | 根据关联预订规则的允许证件范围开放；直接扫码也受同一范围约束 | 按该票现有规则校验，包括允许证件及实际适用的购买限制 | 必须通过 |
| 非实名票 | 允许主动添加游客，选择服务码或直接扫码；不强制填写 | 不校验票品对应购买规则，不因没有勾选允许证件而拦截 | 主动填写后必须通过，不能因非实名免除 |

执行顺序：

1. 读取当前票品实际关联的预订规则，先明确是否实名。非实名不能被误判为“允许证件集合为空，全部拒绝”。
2. 输入服务码后，两种票都须完成后端验签解析及官方类型到业务类型的正确映射。未知或尚未支持的官方类型不默认当护照或回乡证。
3. 实名票再按实际关联规则校验允许证件及适用的其他购买限制；不使用全局证件集合或测试小样默认全选替代。非实名票跳过票品对应购买规则。
4. 所有适用校验通过后，才接受身份并回填真实类型、姓名、号码及性别。解析失败、类型无法映射等，无论是否实名，都保持服务码状态、提示并阻止作为有效资料提交；售票员可清空或改选普通类型按已定规则重新录入。
5. 前后端使用一致的实名分流、类型映射及适用校验。不能因前端回填或非实名标记绕过服务码自身校验。

“服务码”仍是采集选项，不另加一个预订规则勾选项代替真实证件资格。实名票按已核实的类型支持与票品允许范围计算入口；非实名票允许入口，实际输入仍受相同服务码校验及保存规则约束。非实名票已有的普通证件录入和校验行为保持现状，本次不重新定义。

**验收补充：**为七个官方类型分别建立映射与资格用例；对照实名票允许/不允许两种配置，以及非实名未配置证件范围的场景，验证入口及提交判断，前后端一致。核对 TY、CF 等类型的号码不会被普通大类旧格式误拦截。仅有 PP/PO 真实签名样码，其他类型可先测映射，但不得将合成映射测试写成真实 SDK 验签已通过。本次新增 CF 须同时覆盖规则配置、窗口下拉、游客保存、查询及旧配置兼容，不能只在窗口增加文字选项。

#### 2.4 三项日期过期暂不阻止购票（2026-11-15 最新更正）

证件有效期至（`zjyxqz`）、签证有效期至（`qzzjyxqz`）、码失效日期（`msxsj`）继续按 SDK 实际结果保存，但本次暂不将三者过期作为不可购票、不可补录、禁止回填或不能提交的条件。三项任一过期或同时过期均按此处理，不因日期过期将已成功验签解析的码判为识别失败。签证日期为 Null 时也不因本项新增必填限制。

解析、数字签名核验、类型映射、实名票的允许证件范围及其他既有适用规则仍执行；不能借此放行损坏码或验签失败码。该更正适用于散客、团队、长期/临时合作伙伴及两处补录；查询继续按第 5.2 节直接匹配已保存原码。

本条覆盖前文及旧首期方案中三项日期过期的购票阻断建议。历史测试不重写为新规则已通过。验收须分别覆盖三项单独过期、同时过期、签证日期 Null，以及过期同时篡改签名、过期同时票品不支持证件：前几种不因日期拦截，后两种仍按签名或票品规则拦截。

### 4. 录入来源、只读及切换清空（当前执行逻辑）

#### 4.1 证件类型与录入来源是两回事

同样显示“护照”的两位游客，可能分别来自人工录入和服务码解析，不能仅凭下拉显示值判断。每位游客须独立保留：

- **真实证件类型**：身份证、护照等，用于票品资格和原有证件校验。服务码解析成功后，此处保存映射后的真实类型，不把“服务码”当作真实证件类型。
- **当前资料来源**：区分人工/既有非服务码录入与成功的服务码解析。来源是当前资料的业务属性，不新增常驻页面字段。身份证设备读取沿用原有流程，不因为外设输入就标为服务码。
- **当前输入状态**：人工录入、等待服务码、解析中、解析失败、服务码成功回填等。正在输入或失败的码，不能标为成功服务码来源。
- **当前有效服务码关联**：原始完整码、官方细分类型、同次完整解析结果及核验结果，与该游客绑定；同原始处理历史区分。

以上是产品逻辑概念，不指定正式字段名或表结构。研发先查现有模型，复用或扩充；不能根据当前证件类型、是否只读、输入长度或历史上是否扫过码来猜资料来源。展示为护照后，服务码来源仍须保留。

#### 4.2 下拉操作判断表

按**操作前的来源和输入状态**判断，再执行所选动作。散客、团队、长期/临时合作伙伴使用同一逻辑。

| 操作前的当前行 | 售票员操作 | 执行结果 |
| --- | --- | --- |
| 人工/既有非服务码录入 | 选择其他普通证件类型 | 完全沿用现有切换与校验，不因本次功能额外清空姓名、号码或性别 |
| 人工/既有非服务码录入 | 再选当前普通证件类型 | 沿用现状，不触发服务码清空逻辑 |
| 服务码成功回填，显示真实类型且身份只读 | 选择任一普通证件类型，含再点当前类型 | 清空当前行身份与有效服务码关联，保留本次选中的类型，转为可编辑的人工录入；不弹确认 |
| 等待服务码、解析中或解析失败 | 选择普通证件类型 | 清空当前行身份、输入码及未完成结果，保留所选类型，转人工；迟到解析结果不得回填 |
| 任一录入来源或状态 | 从下拉选择“服务码”，含再次选择 | 清空当前行身份及有效服务码关联，进入空白服务码输入状态，等待新码；不弹替换确认 |

**清空范围**：姓名、显示的证件号码、性别、原码输入、当前有效服务码关联、待确认解析结果及当前错误提示；解除身份字段只读。保留游客行、稳定关联身份、票品、票数和其他游客。不删除原始处理历史，也不让旧历史继续充当本行有效关联。选普通类型时保留新选类型；选服务码时下拉显示服务码，输入框为空。

一次下拉选择直接完成切换，不增加“转人工”中间操作。再次点击同值也须能识别操作，不能只监听值变化。

#### 4.3 解析回填与直接扫码

- 完整码经后端验签解析、类型映射及适用的票品规则校验后（非实名票不校验票品规则），才回填真实类型、证件号、姓名、性别；原码另行保留，当前来源置为成功服务码来源，身份字段只读，下拉仍可操作。
- SDK 返回后自动把下拉从服务码切成护照等，是**程序回填**，不是售票员主动选择，不能因此触发清空。实现必须区分程序回填和用户下拉操作。
- 不切下拉而在已有人工资料行直接扫码，沿用已确认的冲突规则：一致则补全；姓名、类型或号码冲突则确认，取消保留原资料和原关联。这个入口不等同于主动选择服务码先清空，不擅自改为静默覆盖。
- 主动选择服务码已先清空，因此新码按空行回填，不再因上一位身份触发替换确认。
- 已进入服务码状态但尚未处理、解析中、失败、证件不适用或冲突待确认，都保持服务码处理状态，不得按当前行原有的普通证件类型绕过校验；不回填成功来源，不可作为有效资料提交。只有全部校验成功且新身份已接受，才显示真实类型与号码。前端显示变化仅是结果，提交仍以该游客当前有效核验状态和关联为判断依据，不能只看下拉已不是服务码。

#### 4.4 提交与挂单恢复

来源、真实身份、原码与解析结果须绑定同一游客，不能按当前行号临时拼接。提交时，服务码成功来源须携带对应原码和解析结果；转人工后不得携带旧码作为当前有效服务码资料。

挂单时保存当前有效的来源和关联；恢复时身份、原码和解析结果一起恢复。成功服务码来源继续只读，人工来源继续可编辑。恢复赋值同样不能误触发用户切换清空。挂单本身不形成供省厅查询的业务记录；正式持久化能力尚待研发核查与实现。

现有挂单仅当天有效，过当天清空（用户确认的系统机制）。当前原资料的码失效时间为日期粒度，因此不增加“跨天恢复挂单导致服务码过期”的场景，也不要求因恢复挂单再次扫码。初次录入与挂单恢复均按本次最新口径，不因下列三项日期过期阻止购票。

### 5. 保存与对外记录

- 保存真实证件类型与号码、服务码采集来源、原始服务码、官方细分类型、完整解析结果及核验结果，并正确关联游客；不自行生成官方码。

- 下单前取得票品校验所依赖的必要解析结果；不依赖的扩展处理可评估后置 job。具体性能与今日实现需核查，不承诺未经测量的无影响。
- **订单侧只排除待付款，其他订单状态不额外筛选或处理。**本条替代前期“必须支付成功才纳入”“未支付一律排除”等表述。实际状态对应由开发查证，不猜状态码。
- 对外扫码时间取订单下单时间；同一次服务码录入关联多张票不按票数复制成多条。独立业务记录不按证件号或原码永久去重。增量记录实际变更及接口技术字段由开发处理，不与产品反复讨论。
- 仅游客源表存在数据不自动扩大为全部普通手填游客均需提供。转人工后原始记录保留，不代表仍与当前游客有效关联；取消替换不改动原关联。
