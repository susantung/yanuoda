# 支付配置化功能方案

功能版本：V3.6｜方案修订：V1.7｜2026-10-23。

配套：[页面清单](01-页面清单.md) · [全程流程图](02-全程流程图.md) · [开发与验收](04-开发核对与验收清单.md)。

## 1. 本次修改范围

本次修改五部分：

1. 后台统一配置支付方式的启用状态、适用场景，以及扫码付/银行卡的资源规则和账号/设备绑定。
2. 窗口按配置显示支付方式；扫码付/银行卡在确认弹窗中带出收款资源和柜台编码/POS编号。
3. **每笔扫码付、银行卡订单新增记录实际使用的资源及柜台编码/POS编号，并在订单的“订单支付”信息中展示。** 合作伙伴充值/回款同样保存并展示本次使用的资源及编号。
4. 冲红接入支付配置，支持换支付方式及扫码付/银行卡同方式更正资源或编号；申请、审核和详情保存展示前后快照，审核同意成功后更新有效支付信息。详见[第24—28节](05-冲红补充方案.md)。
5. 内导计时结账补收接入同一支付配置；开单与补收逐笔记录资源及编号，订单详情、交易记录和异常查询保持一致。详见[第29—33节](07-内导结账补充方案.md)。

**所有支付方式确认后的下单、收款、账户处理、出票等均沿用原逻辑。本次不改支付接口、订单状态、扣款、计费、押金、结算、退款或打印逻辑。**

## 2. 公共规则

### 2.1 统一配置与场景

一种支付方式只维护一份资源归属和使用方式，所有适用场景共用。扫码付、银行卡可分别选择不同归属。

场景为：散客售票、团队售票、长期合作伙伴、合作伙伴充值/回款、内导售票。内导散客/团队属于同一场景的业务子类型，不拆绑定。

资源及绑定按当前景区管理；账号取当前登录账号，设备取实际窗口设备，不用账号档案的绑定窗口代替实际设备。

### 2.2 支付方式白名单

“可选”表示后台可勾选，窗口还需满足“已启用＋包含当前场景”。

| 支付方式 | 散客售票 | 团队售票 | 长期合作伙伴 | 充值/回款 | 内导售票 | 原收款处理 | 本期资源 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 现金 | 可选 | 可选 | 不允许 | 可选 | 可选 | 线下支付 | 无 |
| 扫码付 | 可选 | 可选 | 不允许 | 可选 | 可选 | 线下支付 | 扫码付柜台 |
| 银行卡 | 可选 | 可选 | 不允许 | 可选 | 可选 | 线下支付 | 银行卡POS |
| 微信 | 可选 | 可选 | 不允许 | 可选 | 可选 | 线下支付 | 无 |
| 支付宝 | 可选 | 可选 | 不允许 | 可选 | 可选 | 线下支付 | 无 |
| 聚合支付 | 可选 | 可选 | 不允许 | 不允许 | 可选 | 线上支付，建行聚合支付 | 沿用原设备关系 |
| 挂帐 | 不允许 | 可选 | 可选 | 不允许 | 仅内导团队 | 账户支付 | 无 |
| 预付款 | 不允许 | 可选 | 可选 | 不允许 | 仅内导团队 | 账户支付 | 无 |

团队允许全部九种；内导散客六种，内导团队九种。长期伙伴仍按原默认账户锁定挂帐或预付款；临时伙伴固定挂帐，不作为可配置场景。

### 2.3 启用及提交条件

- 适用场景至少选一个；每个正式场景至少保留一种已启用方式。内导散客须至少保留一种普通支付，不能仅剩账户支付。
- 停用或取消场景导致无可用方式时阻止保存，指出具体场景。
- 支付方式可显示，不代表资源已就绪。缺资源不拦主页面“确认下单”；在支付确认弹窗内提示，阻止该方式最终提交，可换其他可用方式。
- 所有原业务校验不变。

### 2.4 资源与统一编号

| 字段 | 本期规则 |
| --- | --- |
| 资源ID | 稳定关联账号/设备绑定及订单，不按名称关联 |
| 资源类型 | 扫码付柜台 / 银行卡POS；编辑不可改 |
| 资源名称 | 必填，同景区不可重名；绑定下拉显示此名称 |
| 柜台编码/POS编号 | 同一个字段；必填文本，保留前导零 |
| 启用状态 | 控制资源可用性，与支付方式启用状态分别管理 |

### 2.5 资源归属与使用方式

| 配置 | 规则 |
| --- | --- |
| 跟收银账号 | 只取当前登录账号绑定；换设备不改变账号资源 |
| 跟窗口设备 | 只取实际窗口设备绑定；换账号不改变设备资源 |
| 固定使用一个 | 绑定一个，该资源即默认；窗口灰显不可切换 |
| 允许多个并默认一个 | 至少绑定一个，指定其中一个默认；窗口允许在有效绑定中切换 |

不跨账号/设备兜底，不自动取第一项。切换归属保留另一方绑定，不自动复制；多资源改固定后，不符合新规则的绑定须重新配置。

### 2.6 编辑、停用、删除与历史

- 改资源名称/编号后，当前绑定及新订单同步读取新值。
- 已有账号或设备绑定的资源不能停用或删除，提示引用主体；须先改绑。
- 无绑定资源可停用或删除，删除二次确认，提交时复核引用。
- 每笔订单保存当时实际使用的资源及编号；后续改名、改码、解绑或删除不回写历史。旧记录无编号显示“—”。
- 最终提交时复核当前配置和有效绑定，失败保留业务内容。

### 2.7 支付方式排序与默认选择

| 项目 | 规则 |
| --- | --- |
| 排序范围 | 同景区每种支付方式维护一个排序序号，所有适用场景共用；支付配置列表及窗口支付下拉、支付按钮均按该序号升序 |
| 加载顺序 | 每个页面先按启用、适用场景及原业务资格取出实际可选方式，再按后台序号升序展示。配置9种就排这9种，配置3种就只排这3种；例如本页只有序号2、8、20，依次显示2、8、20，默认选2，不补号、不要求连续，不使用其他页面的第一种 |
| 默认支付方式 | 散客、团队、内导首次进入，以及充值和内导补收新开弹窗尚未选方式时，默认选本次候选排序后的第一种，不再写死现金；开单确认弹窗沿用主页面已选方式 |
| 原业务锁定 | 长期伙伴仍锁定原默认账户对应挂帐/预付款，临时客户仍固定挂帐；排序不改变账户及支付资格 |
| 排序与资源 | 第一种方式缺资源时不自动跳到现金或下一种；沿用弹窗内资源提示及校验，收银员可主动换方式 |
| 已选方式 | 当前业务手工选择、页面暂存或挂单恢复的方式仍有效时保留；配置刷新只重排，不强制切换。已选方式停用或不再适用时，改选过滤排序后的第一种并重置对应草稿资源 |
| 冲红申请 | 可选方式按相同规则排序，仍需申请人明确选择，初始为空，不自动提交或更正 |
| 唯一性与存量 | 同一景区全部支付方式的序号不可重复（包含停用方式），修改自身原序号除外；重复时阻止保存并提示“排序序号已被其他支付方式使用，请更换”；首次上线按原支付配置列表顺序初始化1—9。异常缺值排在有值之后并按原顺序展示，不因缺值中断加载 |

无可用支付方式时沿用无可用方式提示，不能回退到写死现金。排序不改历史订单支付信息。

| 对应页面 | 排序与首次默认 |
| --- | --- |
| W01散客售票 | 仅取本页可用方式，支付下拉升序；首次选本页最小序号 |
| W02团队售票 | 仅取本页可用方式，最多九种；支付下拉升序，首次选本页最小序号 |
| W04散客/团队确认 | 支付按钮与对应售票下拉同序；沿用主页面已选方式，不在打开确认时覆盖用户选择 |
| W11内导散客/团队 | 分别按当前团散资格取方式，支付下拉升序；首次进入、切换团散类型时选对应列表最小序号 |
| W12内导确认 | 与当前内导销售页同序，沿用其已选方式 |
| W18内导结账补收 | 按当前订单团散及账户资格取内导候选，升序并默认本次最小序号；不复用原押金方式或资源 |
| W09共用充值/回款 | 从该场景可用的五种线下方式中取值；每次新开弹窗升序展示并选最小序号，各入口一致 |
| W05/W07合作伙伴账户售票 | 原业务仅允许一个账户支付时仍锁定该方式，不因其他页面的较小序号换账户 |
| W10挂单恢复/页签返回 | 恢复当前有效的已选方式；失效才重选本页可用方式中序号最小的一种 |

## 3. B01｜支付配置列表

[打开原型：支付配置](prototype/admin/index.html?page=payment)

### 3.1 入口与结构

配置中心 → 支付配置。统一展示全部九种支付方式，不按散客、团队拆标签，不设支付查询、配置状态或当前景区副标题。

| 列 | 显示与来源 |
| --- | --- |
| 排序序号 | 第一列，显示已保存的正整数；列表按序号升序，序号不可重复 |
| 支付方式 | 现有字典名称，不提供新增、删除、改名或改编码 |
| 启用状态 | 当前支付方式开关，启用蓝色、停用灰色 |
| 适用场景 | 当前已选场景标签，允许换行 |
| 收款处理 | 线下支付 / 线上支付 / 账户支付 |
| 对接方式 | 按3.3逐项固定对应，不提供任意选择 |
| 资源归属 | 扫码付/银行卡显示配置；聚合支付显示现有设备关系；其他“—” |
| 资源使用方式 | 仅扫码付/银行卡显示固定或多资源规则 |
| 操作 | 所有方式均保留“配置” |

### 3.2 操作与状态

- 点开关直接提交启停；请求中禁重复点，成功更新，失败保持原值并提示。
- 停用前按变更后的全量配置检查五个正式场景；内导还须保证散客子类型至少一种普通方式，不能仅剩账户支付。任一场景变成0种，阻止并指出场景，如“无法停用：内导售票（散客）将无可用支付方式”。服务端同样执行，不依赖前端开关回滚。
- 点配置进入B02，不改变当前配置；保存成功刷新该行；取消不改动。
- 排序序号在B02修改；保存成功后列表立即重新排序，窗口后续加载按新顺序使用；失败或取消保持原序号。
- 加载失败显示失败和重试，不能用“默认全部启用”冒充已保存数据。空配置提示初始化异常，管理员修复，不让窗口静默放行。

## 4. B02｜配置支付方式弹窗

[打开原型：支付配置 → 配置](prototype/admin/index.html?page=payment)

### 4.1 公共字段

| 字段 | 控件 | 默认 / 校验 |
| --- | --- | --- |
| 支付方式 | 灰色只读 | 当前方式名称；不允许改字典 |

### 4.3 固定值、当前值与首次样例分开

- 已有配置：每次打开均回显该支付方式已保存的启用状态、场景、资源归属和使用方式；不重置为样例值。截图中银行卡“跟收银账号＋允许多个”就是当前配置，不是银行卡固定规则。
- 场景下拉：勾选已保存场景，未勾选的合法场景仍可选；固定白名单不随勾选变化。取消/关闭后重开，恢复保存前的值。
- 收款处理和对接方式：始终按3.3映射，不跟着场景、启停或资源归属改变；不得切换线下/系统/账户支付。
- 未保存过配置的原型样例：九种方式均启用，各自合法场景全部勾选；扫码付为“跟窗口设备＋允许多个并默认一个”，银行卡为“跟窗口设备＋固定使用一个”。这两种方式都允许管理员改选，不是固定限制。
- 上述首次值仅描述现有原型样例，不作为生产初始化决定。已有景区保留原配置；新景区初始启停、勾选及资源规则需确认后初始化，不能从截图或测试数据推定为生产默认。

### 4.4 配置、保存及取消

1. 打开当前方式，创建草稿，按4.2显示字段并回显已保存值；修改草稿不立即改变列表或窗口。
2. 场景多选至少保留一项，停用时也不能清空；只能提交3.3的合法选项。
3. 仅扫码付/银行卡校验资源归属、使用方式已选择；其他方式不校验隐藏项，不允许提交篡改的固定收款处理或对接方式。
4. 用修改后的全量配置检查各场景至少一种；内导散客须仍有普通支付。失败留在弹窗并指出具体场景，原配置不变。
5. 成功只更新当前支付方式的可编辑配置，列表同步显示；不改其他方式、不复制或清空账号/设备资源绑定。切换资源规则后的绑定处理按2.5执行。
6. 取消、关闭不保存；保存失败保留草稿供修正或重试。支付确认以后的处理仍完全沿用原逻辑。

### 24.2 弹窗内容与字段取值

保留原订单基础信息、团队信息、订单状态及原因区域。订单基础信息、订单支付信息仍为无边框三列。

| 区域 / 字段 | 显示、取值与交互 |
| --- | --- |
| 订单支付信息：收款资源 | 原有效方式为扫码付/银行卡时新增，只读；取订单当前有效支付记录的资源名称快照，不取本次申请选择值或当前绑定 |
| 订单支付信息：柜台编码/POS编号 | 与原资源一并显示，只读；取同笔支付记录的编号快照，历史无值显示“—” |
| 冲红申请售票员 | 当前发起申请的登录账号，只读；与订单原售票员分别展示 |
| 冲红申请来源 | 发起申请的实际窗口设备，只读；与订单原销售来源分别展示 |
| 上述两项布局 | 在冲红调整信息第一行，占三列网格的第一、第二列，第三列留空；与上方信息及下一行控件列起点对齐 |
| 冲红后支付类型 | 必选；按26.1取候选后按后台排序序号升序，初始不选、不默认最小项；位于下一行第一列 |
| 收款资源 | 仅新方式为扫码付/银行卡时显示、必填，位于第二列；分别取扫码付柜台/银行卡POS |
| 柜台编码/POS编号 | 仅新方式需要资源时显示，位于第三列；随资源自动带出，只读，按文本保留前导零 |
| 冲红申请原因 | 沿用原选填，最多500字，整行显示；切换方式不清空原因 |

弹窗沿用900px宽、居中、24px内边距，正文最高60vh并内部滚动；取消申请/提交申请位于正文外。窄屏按网格换行，不横向溢出。

### 24.3 资源加载、默认与切换

| 条件 / 操作 | 处理 |
| --- | --- |
| 跟收银账号 | 读取申请时当前账号的绑定；不按订单原售票员重新取值 |
| 跟窗口设备 | 读取申请时实际窗口设备的绑定；不用账号档案中的绑定窗口替代 |
| 资源候选 | 仅当前景区、匹配类型、已启用、编号非空且绑定给该主体的资源；不跨主体或类型兜底 |
| 固定使用一个 | 恰好一个有效绑定且默认有效，名称灰显不可切换，自动带出编号 |
| 允许多个并默认一个 | 带出有效默认；下拉支持输入名称搜索，仅在有效绑定中选择，不允许输入新资源或手填编号 |
| 无绑定、默认失效、数量不符或编号缺失 | 在申请弹窗资源区提示，阻止提交；不自动取第一项，可换其他允许方式 |
| 切换支付方式 | 清除上一方式的草稿资源和编号，按新方式重新加载；非扫码付/银行卡隐藏资源区且不提交残留资源 |
| 弹窗期间配置、绑定、资源名称或编号变化 | 提交时提示重新确认；刷新资源后由申请人明确重选，不静默替换或提交旧编号 |

### 24.4 提交与取消

提交时复核原申请资格、订单有效支付信息、可选方式及资源配置。以**支付方式、资源ID、编号**比较是否调整；三者均未变化时提示“支付信息未发生调整”，不创建申请。历史缺编号的原记录可选择当前有效资源补正，仍须审核。

通过后保存待审批申请：订单关联、调整前后支付方式及资源ID/名称/编号快照、申请账号、实际设备、订单业务场景、申请时间及原因。资源解析主体一并留存，供审核复核；此时不修改订单有效支付信息。

保存失败保留草稿；重复提交不产生多条待审批申请。取消或关闭不保存、不改变订单。

| 校验 / 结果 | 处理 |
| --- | --- |

### 31.1 字段、取值与默认

| 字段 | 显示与取值 |
| --- | --- |
| 支付方式 | 可输入筛选的必选下拉。取已启用、包含“内导售票”且符合本单团散及账户资格的方式；散客最多六种，团队最多九种。按配置序号升序，允许跳号、序号不重复 |
| 支付方式初值 | 每次新进入默认本次候选中序号最小的一项；不取原押金方式。无候选留空，提示“当前场景无可用支付方式”，禁止确定 |
| 收款资源 | 仅扫码付/银行卡显示。按当前结账账号或实际窗口设备取已绑定、启用且类型匹配的资源；不取开单人/开单设备绑定 |
| 资源默认与选择 | 固定使用一个：只读；允许多个：默认绑定默认项，可输入筛选切换。无资源或默认失效在本弹窗提示，禁止该方式确定；不跨主体取资源、不自动改成现金 |
| 柜台编码/POS编号 | 仅扫码付/银行卡显示，跟随资源自动带出，只读 |
| 动态字段 | 现金显示原实收/找零；扫码付/银行卡显示资源/编号；其他方式不显示资源字段。隐藏字段不占位、不校验 |

### 31.2 选择与确认

- 同一次弹窗内保留有效手选值；仅调整排序不重置。方式失效时改选剩余候选第一项；切换扫码付/银行卡重新读取对应资源，不串用草稿。
- 确定时复核方式及账户资格；扫码付/银行卡增加资源归属、绑定、启用、默认规则和编号校验。失败留在本弹窗，不新增成功收款。
- 通过后执行原支付处理，本笔金额取结算结果中的补收金额。补收资源及编号独立保存，不覆盖原押金快照。
- 未提交时取消返回W17；重新进入重新加载候选和资源。

- 资源只从申请账号或实际设备的有效绑定中取值；无默认不取首项，固定一个不允许切换，多资源支持名称搜索。
- 切换方式清除旧资源；配置、绑定或编号变化须重新确认。保存前再校验，取消不创建申请，重复提交不生成多条待审批。

## 十、后台审核：复核、生效与驳回

打开原型：[B10冲红审核 → B11同意 / 驳回 ↗](prototype/admin/index.html?page=reversal)

```mermaid
flowchart TB

  ACTION -->|驳回| REJECT[原原因说明校验；保存驳回结果，有效支付不变]
  ACTION -->|同意| STATE{仍待审批且原资格、有效支付未变}
  STATE -->|否| STOP[提示刷新，不覆盖当前订单]
  STATE -->|是| VALID{按申请主体复核方式、场景、绑定及资源快照}
```

图下处理规则：

- 同方式更正的列表前后类型可以相同；进入原审核弹窗查看具体资源差异，不增加列表资源列。
- 审核人只能同意/驳回，不能改申请值；资源复核始终使用申请记录的主体，不使用审核人的绑定。
- 名称、编号、归属或绑定等配置变化时，不静默替换资源；驳回不受失效资源阻拦。
- 新方式无需资源时，生效支付清除柜台/POS关联；原值保留在历史。失败、重复审核不能造成半完成或重复账务处理。
