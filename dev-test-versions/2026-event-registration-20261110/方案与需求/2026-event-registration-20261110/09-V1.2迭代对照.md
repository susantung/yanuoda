## 历史规则与V1.2变化依据

2026-11-10研发评审方案R22原文明确：仅修改已签人员姓名使该人原签署失效；修改手机号、身份证或其他非姓名资料不触发重签。见[评审基线差异文件中的R22原文](assets/评审基线正文差异.diff)。这不是“改任何资料都重签”。

**2026-11-25最新确认**：V1.2保留历史“仅改姓名重签”的口径，撤回此前将身份证变化也纳入重签的扩展。姓名变化并重新暂存成功后，才作废该人的旧签名、旧邀请及旧账号关联；身份证、电话、紧急联系人等非姓名资料修改不重签、不作废分享、不解除账号关联，仍需暂存并执行原资料及门票资格校验。旧邀请失效页仅对应姓名变化，不能用它处理普通资料变更或其他微信已签署的冲突。

## V12-01｜处理规则

1. 适用于主报人尚未下单、尚未提交成功的报名。收费已创单待付款或报名成功后禁止改人；原未付订单实际关闭后恢复未提交规则。已取消继续报名沿既有规则处理，不覆盖原提交快照。
2. 姓名已保存值发生变化，重新暂存成功时生效。仅编辑输入框、保存失败或值未改变，不作废现有状态；结果未知先回查保存结果，确认前不开放新签署/分享。
3. 生效时仅作废该人的旧签名、全部历史分享链接及旧接收账号关联；其他人不受影响。电话、紧急联系人等其他资料变化不触发重签。
4. 旧接收人不能再通过旧链接、已打开页面、我的报名或直接访问查看本份资料及签名、继续签署。服务端重新校验权限；旧页面下一次读取或操作时清除已展示资料，提示“参赛者资料已变更，请联系报名发起人重新分享”。
5. 全部资料完整且成功暂存后，主报人重新分享指定人员；新接收者按本人流程阅读材料、授权并签署，不继承旧接收人的身份或阅读进度。分享完成不等于已签，须实际保存签名成功。
6. 旧接收者正在绘图也不能绕过：确认时复核当前人员资料版本与授权。旧签名先保存、换人后保存时须随换人作废；换人先保存、旧签名后确认时须拒绝旧请求。主报人提交同样校验当前有效签署与资料版本。换人保存、作废旧签名和撤销权限必须保持一致，不能出现新人员配旧签名或旧账号继续有权的中间结果。
7. 该人重签前不允许最终提交；新签保存成功后更新人数及状态，不改动其他人签名。暂存、分享、签署失败可重试，不能假报成功。

## 分享、签署与绑定的统一口径

**V1.2补充 · V12-01（签署后绑定与重复分享）**：分享指定某份报名内的某一位参赛者；发送、打开链接、阅读材料均不绑定账号，仅在分享接收者实际签署保存成功时建立该微信账号与该人员的有效关联。分别分享不同人员互不覆盖；同一人员重复分享不清除已有签名、不解除绑定。该人尚未绑定时，多个微信可以打开有效邀请，最终只允许一个账号先完成有效签署并绑定；其他账号后续进入、读取资料或确认签署时，提示“该参赛者已由其他微信完成签署，请联系报名发起人确认”，不展示整组资料、签名或开放签署。原有效账号可按既有规则继续本人流程，已下单后不可重签。签署保存与绑定必须作为同一成功结果，失败不生成绑定；并发确认只允许一个账号成功，不允许后来者覆盖。姓名变化并暂存成功后，再按本节作废该人的旧签名、所有旧邀请及旧账号关联，之后从原“分享签署”按钮重新发送。

| 操作／状态 | 处理方式 |
| --- | --- |
| 分别给第1人、第2人发邀请 | 每份邀请对应各自人员，不因再次分享覆盖前一人的目标 |
| 同一人员邀请发给A、B，两人均未签 | 发送和打开不绑定；谁先完成有效签署并保存成功，关联谁，系统不据此声称已核验实际落笔人 |
| A签署成功后，B打开或提交 | 拒绝覆盖A的绑定；即使B之前已打开画布，确认时也须重新检查并拦截 |
| 原绑定账号再次打开 | 按本人有效权限继续；可重签时沿原流程重签，不误报其他账号冲突 |
| 再次发送邀请 | 复用该人原“分享签署”按钮，按钮名称仍为“分享签署”；“重新分享”是再次操作，不是新增按钮，不自动解除已有绑定 |
| 姓名变更并保存 | 先使该人旧签名、全部旧邀请及旧关联失效，再重新分享；新接收者重新按本人流程阅读、授权和签署 |
| 同机签署 | 可以打开各人员签署入口，由各人分别签署，笔迹保存到对应人员；系统不识别实际落笔人、不把同机全部人员自动关联到当前微信。本人签署属于业务告知 |

**两种提示必须区分**：

- 资料变更导致邀请失效：标题“这份签署邀请已失效”，原因“参赛者姓名已变更”，引导联系发起人获取新邀请。
- 同一人员已由其他微信签署：提示“该参赛者已由其他微信完成签署，请联系报名发起人确认”。不能误报为资料已变更，也不能只靠重发邀请解除原绑定。

## V1.2逐页详细方案

本节各页统一属于 **V1.2新增 · V12-01**。页面沿用既有结构；主报人修改资料后重新暂存，再由指定的新接收者阅读并签署。页面中的“本人”由当前有效身份与人员关联确定，不能仅凭姓名相同或持有旧链接判断。

### C03｜填写参赛资料与暂存

**入口**：主报人从报名流程、我的报名→继续报名返回原报名记录。沿用同一份报名，不因修改人员另外新建报名。

| 区域／动作 | V1.2详细规则 |
| --- | --- |
| 可编辑条件 | 主报人在未提交阶段可编辑；收费已创单待付款、报名成功后只读。原未付订单实际关闭后恢复未提交规则。已取消继续报名沿原规则恢复编辑，原提交快照保留 |
| 允许修改字段 | 沿当前项目报名资料模板。姓名已保存值发生变化触发本次失效规则；未配置身份证时不新增身份证输入项 |
| 编辑中 | 输入尚未保存，不作废已保存签名、分享及关联。当前输入与已保存资料不一致时，仍按既有规则要求先暂存，再签署／分享或提交 |
| 暂存按钮 | 点击后保存当前整份资料；保存期间禁用重复点击。允许半填暂存，但资料不完整时不开放签署及分享 |
| 暂存成功 | 对比保存前后的姓名值；发生变化的人员作废旧签名、全部旧分享及旧接收账号关联，其他人员不受影响；页面显示最新已保存资料并刷新签署进度 |
| 未发生身份变化 | 值未改变、编辑后恢复原值，或只改电话、紧急联系人等，不使旧签名和关联失效 |
| 暂存失败 | 显示“暂存失败，请重试”，保留编辑内容；旧保存资料、签名和授权保留，不提示已完成换人 |
| 结果未知 | 回查本次保存结果，确认前不开放新签署、分享或最终提交；按回查到的最终结果恢复对应状态，不能先假定保存失败后重复生成分享 |
| 完整性恢复 | 全员资料完整且成功暂存后，开放该人的去签署／分享签署；该人重签前不允许最终提交 |

**对应验收**：V12-01-01、02、03、04、08。重点核对“编辑发生”和“保存成功”两个时点，不能在输入姓名时提前清除旧签名。

### C04｜签署进度与分享入口

**位置**：继续沿用参赛资料页中的签署进度组件，不新增独立进度页面。

| 区域／动作 | V1.2详细规则 |
| --- | --- |
| 人员行 | 展示该位置当前已保存人员的姓名及有效签署状态；身份变化保存成功后，该人显示未签署，不能回显旧人员签名 |
| 已签人数 | 只统计当前人员资料对应的有效签署。原来已签的人失效后从人数中扣除；原来未签的人变更不重复扣减 |
| 其他人员 | 保留原签名、已签状态、分享与有效账号关联，不因同组一人换人全部重签 |
| 去签署／分享签署 | 全员资料完整并暂存成功才开放；支持同机分别打开各人员签署入口，也可分享签署；系统不判断实际落笔人，签名保存到对应人员。已保存签名的查看权限沿原规则，仅本人可查看 |
| 再次分享（复用原按钮） | 按钮仍名为“分享签署”，没有独立“重新分享”按钮。邀请指向当前已保存人员，不在发送或打开时绑定微信；资料未变更的重复发送不解除已有绑定。换人暂存成功后，通过此按钮发送新邀请 |
| 分享后的进度 | 分享成功不计作已签；新接收者实际确认且保存签名成功后，该人更新已签，重新计算全组进度 |
| 未签齐 | 保留逐人签署入口，最终提交仍受全员有效签署校验 |

**对应验收**：V12-01-01、02、04、07、09。

### C02｜重新分享后的材料阅读

**入口**：新接收者打开主报人重新发出的有效分享。

| 场景 | V1.2详细规则 |
| --- | --- |
| 进入前 | 校验邀请的目标人员、资料版本及当前关联；资料变化则显示邀请失效页；已由其他微信签署绑定则显示签署冲突提示，均不返回整组资料或签名 |
| 有效分享 | 按当前项目既有顺序和阅读方式阅读材料；保留原有倒计时或滚动条件，不另加新阅读方式 |
| 阅读进度 | 按新接收者本人记录读取，不继承旧接收人的进度，也不直接借用主报人的已读状态 |
| 完成阅读 | 进入接收者参赛资料页，全部人员资料只读，只开放指定本人签署 |
| 阅读中换人 | 下一次读取资料或操作时重新核权，失效后停止原流程，清除已展示的受限资料并显示失效提示 |

**对应验收**：V12-01-05、07。重新分享不等于自动完成阅读或自动认领该人员。

### C05｜分享接收者资料页

**入口**：有效分享接收者完成本人材料阅读后进入，或返回本人签署流程。

| 场景／动作 | V1.2详细规则 |
| --- | --- |
| 展示内容 | 读取当前成功保存的整组资料；保持原方案全部N人只读，仅指定本人有去签署／重签署入口 |
| 身份关联 | 仅在实际签署保存成功时建立接收账号关联；发送、打开和阅读均不绑定。保存失败不绑定，不继承旧人员账号关系 |
| 已签账号冲突 | 同一人员已由其他微信签署绑定时，不展示整组资料或签名、不允许覆盖；进入、读取及确认时均复核，显示签署冲突提示。原绑定账号正常进入不误拦截 |
| 旧分享打开 | 姓名变化已保存后，此前该人全部分享均无效；不展示整组资料、旧签名或签署操作 |
| 已打开页面 | 下一次资料读取、页面恢复访问或签署操作时复核当前授权；失效即清除受限展示，不能只隐藏签署按钮后仍展示整组资料 |
| 失效反馈 | 使用完整状态页：白底、主题色资料更新图标；标题“这份签署邀请已失效”，原因“参赛者姓名已变更”，引导“请联系报名发起人／获取新的签署邀请后再来吧”。不展示参赛者资料，不允许旧链接自行选择新人员或通过刷新取得新权限 |
| 失败与权限区分 | 查询失败不能直接当作分享有效或已确认失效；提示按原加载失败方式重试，拿到有效结果后再展示受限数据 |

**对应验收**：V12-01-05、07。账号访问范围须由服务端控制，前端提示不能替代权限撤销。

### C05｜本人手写签署页

**入口**：主报人或分享接收者按原有本人权限进入纯签署页。仍保留原画布、后台配置签署说明、清空和确认签署。

| 场景／动作 | V1.2详细规则 |
| --- | --- |
| 进入签署 | 读取当前有效人员资料与签署授权。旧人员已失效时不能打开其旧笔迹给新人员使用 |
| 确认签署 | 除既有非空笔迹校验外，复核人员版本、邀请、当前微信与既有绑定。尚无绑定时签署和账号关联一并成功；同账号按原规则处理；已有其他账号绑定时拒绝并提示，不覆盖。并发只能一方成功，失败不标已签或建立绑定 |
| 签署先成功、换人后成功 | 随后换人保存成功时，作废刚保存的旧人员签名及授权，最终该人仍为未签署 |
| 换人先成功、旧签署后确认 | 拒绝旧请求，不把旧签名保存到新人员；清除受限页面内容并显示资料变更提示 |
| 签署失败 | 不更新已签，不恢复旧授权，不影响其他人员签名；当前授权仍有效时可沿原页重试 |
| 签署成功返回 | 回本人只读资料页刷新进度；主报人下一次读取时同步最新有效签署，不自动统一提交报名 |

**对应验收**：V12-01-06、07、09。前端正在显示画布不代表仍具有保存权限。

### C06｜立即报名与最终提交

**入口**：主报人在参赛资料页完成全员资料与有效签署后点击立即报名。

| 场景 | V1.2详细规则 |
| --- | --- |
| 前端可提交条件 | 当前资料已完整保存，需签署项目全员均有与当前人员资料对应的有效签署；换人后未重签不得提交 |
| 服务端最终校验 | 即使绕过前端按钮，也须校验当前资料及签署有效性，再执行原报名时间、名额、资格与下单校验 |
| 提交与换人并发 | 提交和换人保存须保证一致；不能让订单使用一版人员资料、有效签名却属于另一版人员。已成功创单后拒绝后到的换人保存；先换人成功则旧版提交不能沿用旧签署通过 |
| 校验失败 | 保留当前资料和其他人有效签署，按错误定位需要补签的人员；不得继续调起支付 |
| 原订单恢复 | 原未付订单实际关闭后可恢复未提交编辑；有效待付款订单仍锁定，不能把关闭微信支付框当作订单已关闭 |

**对应验收**：V12-01-08、09。原订单、支付及成功海报流程继续沿用既有方案。

### C09／C10｜我的报名与共用资料查看

**入口**：主报人或有效关联组员从我的报名进入，或直接访问原资料页。

| 身份／场景 | V1.2详细规则 |
| --- | --- |
| 主报人 | 原报名继续保留；符合未提交编辑条件时可继续完善、重新分享并提交 |
| 被更换的旧接收账号 | 对应关联撤销，不再以该人员身份展示或访问本份报名、整组资料及旧本人签名；列表刷新重新核权，直接访问同样拦截 |
| 旧账号已有详情页 | 页面恢复访问或下一次读取／操作时重新核权；确认失效后清除受限资料，显示相同资料变更提示 |
| 新接收者 | 完成本人授权签署流程后，按原有效组员规则关联、查看全部N人只读资料，仅可查看本人签名 |
| 其他有效组员 | 既有有效关系保留，沿原权限查看，不因其他人换人解除整组全部账号关联 |
| 同账号有其他有效身份 | 仅撤销被更换人员这一条关联；若当前账号同时具有主报人或其他仍有效的本人权限，仍按有效身份授权范围访问，不误删合法权限 |
| 已提交历史 | 待付款、成功报名不能直接换人；原提交快照、历史订单及金额不被草稿修改覆盖 |

**对应验收**：V12-01-04、05、07、08。原型只提供旧接收者访问结果模拟，真实账号列表与服务端权限尚待研发实现及验收。

### 共同保存与状态要求

人员资料保存、旧签名作废、旧分享撤销、旧账号关系撤销须作为同一成功结果处理；失败不得部分生效。仅该人失效，原报名和其他人员保持。保存结果未知先回查，重复请求不得重复建报名、重复认领或恢复已撤销授权。版本、授权标识及接口具体字段由研发确定，不以本地原型变量作为正式接口契约。
