# 赛事活动报名｜公共业务规则

本文件维护跨页面共同使用的规则。页面只说明本页字段和动作，不反复复制公共正文。

## K01｜对象、人数与数据口径

| 对象 | 关系与规则 |
| --- | --- |
| 赛事 | 一场赛事下有多个项目；维护举办时间和介绍，不再设赛事统一报名时间 |
| 报名项目 | 独立报名/比赛日期、固定单次N、模板、签署要求、项目名额、免费/收费 |
| 收费报名项 | 一条关联票配置对应一个报名展示名称，最多20字；游客选该项，后续使用该原票，固定购买1张 |
| 免费项目 | 不关联门票、不做无票收款，不虚构报名项、票名、订单、支付或核销码 |
| 一份报名 | 固定N人共用一份报名，收费共用一笔当前有效订单；一份成功报名生成一张海报 |
| 示例与运营值 | 当前2027年1月3日、双人项目、500/398价格等为示例。实际名称、人数、价格、材料、图片均取正式配置 |

N为固定正整数，本期同项目只支持一种N，游客不可增减人数或购票数量。人数规则不同可拆项目，早鸟/正价则可为同项目的不同关联票项。

成功人数只统计收费实际付款成功或免费提交成功的人数，一份N人成功计N；暂存、签署、待提交、待付款均不计成功人数。项目显示成功人数/总名额；不限显示“成功人数/不限”。赛事按各项目汇总；任一项目不限则分母不限，无不限但有项目未完成名额配置则显示未配置，不把未知当0。

## K02｜时间、可用性、名额与占用

### 本规则在哪些页面使用

| 页面 | 使用位置与职责 |
| --- | --- |
| [C01赛事总览与报名项选择](05-小程序逐页功能方案.md#C01-赛事总览与报名项选择) | 直接按该页详细判断表显示未开始、已截止、已满员、已售罄或报名中，并决定可点与箭头；列表不创建报名订单、不占名额 |
| [C06统一提交](05-小程序逐页功能方案.md#C06-统一提交与下单节点) | 最终提交重新校验最新项目可用名额和所选票库存，服务端并发控制占用；不信任列表旧状态 |
| [B08关联门票](03-后台逐页功能方案.md#B08-关联门票) | 首次容量匹配：票库存折算人数不得小于项目名额，允许大于；不是运行时名额控制 |

项目可用人数按“总名额−成功人数−有效待付款临时占用人数”计算，最低为0；项目不限时不判人数不足。各收费选项共用项目名额，但分别检查自己的票库存。列表详细展示与具体示例见C01，不需读到提交环节才知道列表状态。

### 时间来源与判断

- 赛事举办日期、项目比赛日期、项目报名窗口、原票可售窗口各有职责。开始不得晚于自身结束；不额外要求报名截止早于比赛首日，不按比赛首日00:00截断。
- 收费报名项有效窗口取项目报名窗口与本票真实可售窗口交集；开始取较晚值，截止取较早值。无交集则不匹配。允许各票窗口衔接、交叉或空档，不合并为虚假的连续时段。
- 免费项目直接使用项目报名窗口。展示可到分钟，交易判断仍精确到秒；当前基线包含起止时刻，真实服务端边界须与票务语义对齐。
- 后台项目时间状态仅“未开始／进行中／已截止”，缺时间“未配置”，不代表有库存、已发布或可下单。游客报名项另判时间、名额和票库存。
- 草稿绑定原报名项，不自动从早鸟换到正价，不保留已过期价格资格。后续提交必须重新检查当时窗口与原票。

### 名额、库存与交易

| 内容 | 规则 |
| --- | --- |
| 项目总名额 | 免费/收费均独立配置限制或不限；有限总人数为N整数倍 |
| 首次票容量检查 | 限制名额时，关联票可用库存张数合计×N不得小于项目总名额，可以更大；存在不限库存票可覆盖有限名额 |
| 后续报名 | 分别检查项目剩余可用人数≥N及所选票库存≥1张；不能拿剩余票库存反比初始总名额 |
| 不限 | 项目不限不能绕过票库存；票库存不限也不能解除项目名额上限 |
| 阅读/暂存/签署 | 不占名额或票库存，不算报名成功，不锁价 |
| 收费下单待付款 | 临时占用，付款成功转正式；失败、实际取消或超时关闭按原交易链路释放，不能重复扣减/释放 |
| 免费提交 | 最终提交时校验项目窗口和名额，成功计入报名人数，无票务占用与支付 |

后台“门票可支持人数”是库存折算展示，不是另一项可编辑报名名额。使用“库存合计张数×N＝可支持人数”。库存-1代表不限，原型99999只是演示，不能据此形成生产库存规则。成功人数不能代替含待付款占用的可用名额。

## K03｜暂存、记录与快照

> **项目内迭代新增V1.1 · V11-02**：全员资料齐且底部暂存成功才开放签署/分享；改资料后再用同一暂存按钮。首次暂存建记录的方向原已存在，本轮补齐本地同一记录保存及恢复。
> **项目内迭代新增V1.1 · V11-03**：暂存成功短暂浮层约2秒，不占底栏；不新增上方保存按钮。


| 动作/状态 | 保存与显示规则 |
| --- | --- |
| 仅打开页面、阅读或完成材料阅读 | 阅读进度独立保存，不生成报名记录，不触发后台配置锁定。**项目内迭代新增V1.1 · V11-12（规则细化）** |
| 普通输入、切换须知标签 | 保留本页内存输入，不自动保存到报名记录 |
| 首次主动暂存成功 | 生成一条报名记录，按资料/签署完整性取资料待完善、待签署或待提交 |
| 后续暂存、签署成功 | 更新同一份记录及对应人员进度，不另建报名 |
| 暂存一半资料 | 允许，不要求全部必填先齐；不能因缺项丢弃已填值。非法格式的完整存储契约待接入核实 |
| 直接离开未保存输入 | 本次未保存变更丢弃；有上次成功暂存则保留上次数据，不删除旧记录；无离开确认三按钮 |
| 进入签署或分享 | 必须全部N人必要资料齐且已成功暂存。暂存后再改资料需使用同一个底部暂存成功后再签/分享，无上方保存按钮 |
| 最终提交 | 资料和必要签署/阅读齐备并通过实时校验后保存提交快照；收费同步下单，免费直接完成 |
| 提交后的资料 | 含待付款，按提交时字段与数据快照展示，不补填之后新增字段 |
| 未提交的资料 | 读上次成功保存值和适用最新模板，新增字段显示，既有已填值保留；按必填规则补齐 |

保存失败不得声称成功或覆盖上次成功数据。签署确认保存与普通资料暂存是不同业务动作，签署不等于最终提交。报名时间取最终报名提交成功时间；前端标签“报名时间”，后台标签“报名提交时间”，不取创建/暂存/支付时间。未提交不编造时间。正式报名编号及生成时机待用户给规则。

> **项目内迭代新增V1.1 · V11-05**：新增C11结构原型：一个框按姓名/手机号/身份证精确OR匹配，只返回成功记录，结果手机号前三后四、中间****。仅C11适用。


复用现有微信/手机号授权，不新增认证体系。通过本人授权并完成本人分享签署后，可关联该账号与本份报名对应参赛者。仅打开/转发链接、同名搜索或同机操作均不能自动认领；同机亲签不等于把所有人员绑定当前微信。真实UID映射与访问校验待接入。

| 身份 / 入口 | 资料范围 | 签名与操作 |
| --- | --- | --- |
| 主报人管理 | 本份全部N人资料 | 未下单可填改、暂存和统一提交；只签本人、不能打开他人签名；可续付有效原订单 |
| 指定分享接收者 | 全部N人只读，N不限于2 | 先按序读材料，只签/重签指定本人；不改任何资料，不分享给其他人签，不统一提交/付款 |

| 后台B10 | 沿原后台权限查看报名及人员资料 | 保留查看和放大签名能力，不沿游客端的他人签名限制撤回后台能力 |

## K05｜配置修改与历史影响

> **项目内迭代新增V1.1 · V11-12（规则细化）**：仅打开页面、阅读或完成全部材料阅读，不生成报名记录，不触发后台配置锁定；阅读进度独立保存。首次主动暂存成功（包括半填暂存）产生报名记录后，才按K05限制后台配置修改。

此触发条件针对项目内是否已有报名记录：某游客仅阅读不解除其他游客已产生报名记录带来的配置限制。已有记录后仍按配置分别判断：资料项不可改删、允许新增；N及是否签署不可修改；有限总名额只增不减；免费/收费及关联票继续按是否产生过相应订单判断，不因首次暂存一律锁定。

> **项目内迭代新增V1.1 · V11-11（规则细化）**：区分后台项目配置限制与游客已填资料的修改权限；暂存产生记录不等于游客资料只读，不改变已确认业务。

本节“已配置资料项不可改删”“单次N、是否签署锁定”均指**后台运营修改项目配置**，不表示游客已填资料不可修改。字段定义（例如是否收集手机号）与游客填写值（例如手机号具体号码）是两类对象。游客数据修改权限按C03/K04/K06判断：主报人未提交可改；成功下单待付款或报名成功后只读；原未付订单实际关闭后恢复未提交可改；组员查看始终按只读权限。下表涉及“修改参赛者姓名”“待付款或成功报名的人员资料与签署”的行，是游客数据规则，与后台模板配置分开理解。

> **项目内迭代新增V1.1 · V11-06**：有限总名额只增不减且仍须N整数倍；限制/不限模式与N仍锁定，不改票库存及旧占用。


| 修改对象 | 允许范围 | 历史/进行中数据 |
| --- | --- | --- |
| 已配置资料项 | 有游客报名记录（包括半填暂存）后不可改删；允许新增，新项本次保存前可改删，保存后同样限制；不额外禁止排序 | 未提交保留旧值并展示新增项；已提交只读提交快照，不追补 |
| 单次N、是否签署 | 首次主动暂存成功产生报名记录后，后台不可修改；仅阅读或完成阅读不触发锁定。**项目内迭代新增V1.1 · V11-12（规则细化）** | 项目是否已有报名记录以服务端实际记录判断，不以阅读进度或本地示例判断 |
| 有限总名额 | 已有报名后只增不减，仍为N整数倍 | 不改原报名/订单/占用，不自动增加门票库存 |
| 限制/不限模式 | 已有报名后不可切换 | 本轮只放开有限总名额增额 |
| 免费/收费 | 尚未产生订单可切换，已有暂存/阅读/签署不锁；已有订单不可切换 | 保留资料进度，最终按当前模式校验；已提交不追改历史 |
| 有过报名订单的关联票 | 不替换、不移除，订单取消或退款也不解除历史限制 | 展示名称和逐项限制说明仍可改；已提交保留当时展示名称，不改历史票/价/人数/订单 |
| 从未产生订单的关联票 | 按该票自身判断可移除重加；不因项目另一票有订单就全部锁住 | 新增关联票允许，旧暂存不自动换项 |
| 报名时间 | 可调整，提示影响未提交报名 | 过期草稿不可提交；延长不延长票售卖期；不自动取消已有成功或仍有效待付款订单 |
| 赛事介绍/报名须知/已有材料正文 | 可改，展示最新正文，不做完整原文版本 | 已读已签保留，不自动重读重签；未完成继续最新正文 |
| 新增签署材料 | 需签署项目仍至少一份 | 未提交补读新增材料，已有有效签名保留；已提交含待付款不追补 |
| 删除签署材料 | 需签署项目仍至少一份 | 未提交不再读被删材料，其他已读已签保留；已提交不追改 |
| 修改参赛者姓名 | 未下单可改 | 仅该人原签署失效，其他人保留；非姓名资料修改不重签，仍须重新暂存后签/分享 |
| 待付款或成功报名的人员资料与签署 | 不可修改或换人 | 未付款原订单实际取消/关闭后才恢复未提交；全额退款后的名额释放和新旧订单关联按本节退款规则执行，不能直接套用未付款取消规则 |
| 比赛延期/取消 | 另专题待讨论 | 不能从允许改报名时间推导已出票使用期或退款政策 |

材料正文变更后保留旧签名，不意味着该签名证明阅读过更新正文。新增资料字段是否触发重签U04本阶段暂不考虑，不与新增材料混为一项。

## K06｜状态、提交与原订单恢复

> **项目内迭代新增V1.1 · V11-07**：主报人资料页底部继续支付进入同一有效原订单；组员/免费无按钮。原未付订单实际关闭才恢复立即报名，取消收银台不恢复；订单关闭回退原则原已存在，本轮补足该按钮衔接。


| 报名主状态 | 判断 | 发起人主要动作 |
| --- | --- | --- |
| 资料待完善 | 已有暂存，必要资料未齐 | 继续报名、补资料 |
| 待签署 | 资料齐，需签署且未全员有效完成 | 继续报名、按保存门槛签署/分享 |
| 待提交 | 资料、必要阅读/签署齐，无有效待付订单或未完成免费提交 | 立即报名 |
| 待付款 | 报名已提交，原订单有效待付 | 资料只读，继续支付进入该原订单，不重复下单 |
| 报名成功 | 收费实际支付成功 / 免费最终提交成功 | 查看资料、海报；收费还可看原订单及核销码 |
| 已取消 **项目内迭代新增V1.1 · V11-13（业务变化）** | 当前绑定的票实际退款成功，不论游客、全域后台或对接票务系统退款（含已检票后强退） | 不计报名成功人数，释放N项目名额；继续报名、查看旧退款订单 |

**项目内迭代新增V1.1 · V11-13（业务变化）**：新增“已取消”报名状态，仅对应当前关联门票实际退款成功；申请、审核、退款中不算取消，未付款订单取消/关闭不使用该状态。项目时间、订单、签署状态仍分别记录。

- 一次立即报名包含报名提交及收费订单提交，固定购票1张、传全部N人资料。订单创建成功就锁全部资料和签署；不等付款才锁。
- 提交中防重复点击，服务端保证重复请求不产生第二有效订单/重复占用；结果未知先回查原请求与订单，不直接重下。跨系统部分成功恢复需研发核实。
- 首次下单成功直接调微信支付，无中间去付款页或第二次订单提交。实际付款成功后直接成功海报；后续原订单补付成功也一样。
- 取消微信支付仍待付款，进入原系统订单详情，整份资料/签署继续锁定。原订单页面及支付、返回、核销能力继续复用；本轮V11-13仅叠加赛事退款截止时间对申请退款入口及提交的限制，不为报名增加其他入口。
- 报名资料页待付款时，发起人底部显示“继续支付”，进入当前有效原订单。没有有效原订单不能继续支付；组员和免费不显示。
- **项目内迭代新增V1.1 · V11-10（规则细化）**：未付款原订单被人工取消或系统实际关闭后，保留报名、资料、有效签署，报名状态恢复未提交；这是业务状态回退，不表示订单页自动跳转，订单页停留与返回沿原系统。用户后续进入或返回报名侧时读取实际结果；资料齐且签署有效时恢复待提交，并在符合当前报名条件时显示立即报名。新必填未补、姓名变更签署失效等按实际完整性处理。
- 重新提交重查当前窗口、资格、价格、项目名额和票库存，不自动换票或恢复旧价。报名已截止不得重新下单；截止前已建且仍有效订单可继续在原订单有效期内付款。
- 实际关闭状态决定回退，本地倒计时不是关闭凭证；支付/关闭冲突先查实际结果，已付不当未下单恢复。原订单超时沿既有配置，不新增固定时长和任务。
- 保留报名与历史交易关联，不物理删除旧订单；后台只展示最新订单，不增加历次关闭订单页面。


### 全额退款、名额释放与重新报名

> **项目内迭代新增V1.1 · V11-13（业务变化）**：游客线上仅处理符合原票退票规则及已配置赛事截止时间的整单全额退款；特殊退费线下处理。退款结果联动同时覆盖全域后台和对接票务系统退款。

- 线上以整份报名为单位，按关联订单实际支付金额全额退；不支持团内单人拆退或部分金额退款。部分退费及不符合本期线上退款条件的特殊情况由业务线下处理，不纳入本次线上原路退款。旧退费总规则不作为系统时间计算依据。
- 主报人进入原订单申请，退票规则、审核配置及原退款流程继续复用；需要审核时，游客申请后按原订单显示逻辑处理，审核中继续占用N个项目名额。非赛事订单沿原规则；赛事订单先按订单中存储的门票退款规则判断，再沿订单→报名项目→赛事实时读取退款截止时间判断入口及提交。截止时间非必填、可随时修改，未设置/存量空值不叠加赛事时间限制。修改后下一次读取立即生效；读取失败与未设置不同。截止前成功提交的申请，截止后仍沿原审核和退款流程，通过后正常退款，不重用新截止时间拦截已受理申请。游客入口限制不用于否定后台或票务系统已经发生的实际退款结果。具体页面规则见C07，赛事配置见B02。
- **只有关联门票实际退款成功后，释放该份报名占用的N个项目名额**，不再计入成功报名占用；申请、审核中、退款中或退款失败均不按成功释放。重复通知、刷新或重试不得重复释放。票库存是否及如何恢复沿原票务退款规则，不以项目名额释放代替票库存恢复。
- 退款成功但尚未重新报名，报名继续关联已退款原订单，主报人仍能查看该订单；不得立即清空旧订单关联。
- 重新报名仍检查当前窗口、资格、价格、项目可用名额及所选票库存。仅在新订单创建成功后，将报名当前关联切换至新订单并解除旧退款订单关联；新下单失败或结果未知时先保留旧关联并回查，不因点击重报提前解绑。
- 旧退款订单始终保留在游客小程序“我的订单”列表中，不删除、不隐藏；解除的是报名与旧订单的当前关联，不是删除订单或抹除历史业务事实。新订单按待付款、支付成功等原规则处理。
- **项目内迭代新增V1.1 · V11-13（业务变化、规则细化）**：仅当前关联门票实际退款成功才将报名改为“已取消”、成功报名人数扣减N并释放N项目名额。不论游客申请、全域后台退款或对接票务系统强制退票（含已检票后退款），处理一致；不得用申请、审核通过或处理中代替退款成功。仅处理匹配当前关联订单/票的退款通知，历史已解绑旧单通知不影响新报名；重复通知不得重复扣人数或释放。
- 已取消继续保留报名资料、有效签署及旧退款订单关联，“我的报名”提供继续报名和查看订单。继续报名恢复原记录进入报名页，按未提交时规则完善资料和签署；退款本身不清空资料、不把记录改成待提交，只有成功重新提交才离开已取消状态。姓名修改仍使对应签署失效。原已提交快照不被草稿修改覆盖。
- 待提交与已取消都可发起提交，但必须重查当时全部条件：未关联票按该项目当前报名时间、资料、必要阅读/签署、资格和剩余N名额校验；关联票再按当前报名项有效窗口及原订单层真实票规则、全员资格/限购、价格、库存与下单校验，已过时间或其他条件不符就失败。失败仍保留已取消和旧退款单；未知结果先回查，不能直接生成另一单。
- 新订单创建成功后才替换旧退款订单的当前关联，并临时占用N名额、变待付款；实际支付成功才计成功人数。旧退款订单始终保留在我的订单。若不关联票，则免费最终提交成功后变报名成功并占用N名额。
- **未付款订单取消区别**：主报人取消订单或系统实际超时关闭，解除当前订单关联，保留资料和有效签署，回待提交（资料/签署变化按原完整性规则处理）；取消微信支付弹窗仍待付款。未付款取消不变已取消。
- 退款后的历史海报访问/分享处理仍在U03待确认，不能用旧海报证明当前报名成功。

## K07｜门票匹配与交易规则继承

### 配置原则

先配报名N与字段，再匹配原票；不从票反向覆盖报名模板。价格、库存、预订限制只读，修改到原票系统处理。后台匹配通过不保证未来可下单，提交仍实时校验。全部N人资料传入原链路，不按旧购票表单的框数截取。

| 原票预订信息模式 | 关联约束 |
| --- | --- |
| 无需游客资料 | 可匹配，仍保留报名N人的资料和签署 |
| 仅一位游客 | 沿既有票模式，不强制N=1，报名全部N人资料仍须传入 |
| 所有游客 | 固定买1张，沿原票模式，不强制N=1，真实契约待验证 |
| 每张券需X位游客 | X必须与N完全相等，不能按X≤N |

姓名始终必填，票未要求姓名不构成不匹配。票要求身份证必填，报名必须配置且必填；票不要求身份证，不因报名额外收集而禁选。其他原票必需字段也须有对应来源。购票联系人手机号取发起人授权手机号，不能拿其覆盖所有参赛者。

报名关联阶段不增加“最低起售量>1就禁选”的规则；最终固定买1张，按原票实际起售量、限购、年龄、地区、性别等校验并返回实际原因。全部N人及对应资格校验是既定业务要求，真实参数/年龄基准待核实，不能退化为只验证第一人。

### 比赛日期、价格、库存与可售期

| 比赛/票类型 | 匹配与取值 |
| --- | --- |
| 单日＋日历票 | 真实已配置日期集合须包含比赛当天；读取当日价格和库存，不拿最早/最晚范围代替完整日期集合 |
| 单日＋固定有效期票 | 使用期覆盖比赛当天；从总库存配置取价格库存 |
| 多日比赛 | 本期只用固定有效期票，完整覆盖比赛起止；不使用日历票或选择日期起X天方案 |
| 日历票开放/截止 | 根据传入比赛日和原预订规则计算 |
| 固定有效期免选日票 | 提前预订逻辑无效，取价格库存中的可售时间；使用有效期与付款可售期分别检查 |
| 可订当日提前X小时的既有文案 | 当前基线按可订当日23:59:59处理，不由文案另加硬拦截；真实接口语义待核对 |
| 固定日期且下单后X天生效 | U06a待核实完整计算；原型暂不支持不等于生产永久禁用 |
| 缺比赛日配置/价格库存记录 | 显示“—”并禁止关联，不用最低价、其他日、0或不限补缺 |

总库存是库存方式，不能等同相对有效期或延迟生效票。已知可售窗口按K02取交集。全域与三方配置一致性人工保证，不新增跨系统配置强比对；报名与最新全域票的兼容检查仍保留。

进入/重开项目编辑、打开选票、最终完成时读取最新票配置重新匹配；最终不匹配须显示原因并阻止完成。游客提交仍查实时票、全部人员资格和库存，不能依赖旧配置结果。真实接口接入见开发清单，不把原型变量当正式字段名。
