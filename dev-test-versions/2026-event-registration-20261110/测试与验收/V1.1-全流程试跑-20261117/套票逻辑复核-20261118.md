# 程程票务套票逻辑复核与本轮测试资源纠偏

复核日期：2026-11-18。

## 结论与证据边界

此前建了15张组合票并授权官网小程序，但没有完成独立套票配置。组合票包含基础票，与套票包含组合票，是两层不同的产品关系。全域填写“每券2位游客”只规定游客信息收集数量，不能代替票务系统套票、子票数量、游客分配和拆单配置。此前将双人测试资源描述为“配置完成”不充分。

本次重新读取本地套票专项原文、相关原型图片、V2.10.1/V2.11.1/V2.13.1/V2.17/V2.19原文及票品配置操作底稿。以下属于资料规则，未表示已在当前QA重新执行验证。资料复核完成后已补建一张双人套票并修改全域132928关联，实际结果见文末；未修改报名订单、方案基线或线上资料。

## 一、产品层级与人数

- 基础票：景点或项目等基础票务资源。
- 组合票：引用基础票，维护规则、价格与库存。包含多个游玩项目不等于可供多位游客使用。
- 套票：在“票务中心→套票管理”独立创建，打包已上架的散客组合票，设置各子组合票数量、主票和实名要求。
- 同一种组合票可配置多张。双人同票种场景可配置一个组合票×2；不同票种场景可配置两个组合票各×1。子票数量合计需与实际需要出票人数及实名模式匹配。
- 专项资料规定每种子组合票数量不超过10；原型提示最多5种组合票，种类上限为可配置项，不能混同为“最多5位游客”。当前QA实际限制须回查。
- 套票仅指定一个主组合票，默认首行；主组合票有多张时，游客信息分配仍需按拆出票号处理。
- 套票产品编码独立生成；专项原文使用“-CT”后缀区分套票。当前测试映射编码TKVYB6400054W来自组合票列表，不能当作已建双人套票的证据。

## 二、子票选择、规则一致性及提示

| 检查内容 | 资料规则 |
|---|---|
| 候选范围 | 已上架的散客组合票；支持名称、编码、库存模式、分类、日期及规则等筛选 |
| 首层一致性 | 消费规则、退改规则、库存模式、售卖日期须满足一致性要求，不符候选置灰；编辑回显和下一步再次校验 |
| 售卖日期比较 | 起始日在当前日期前时按当日00:00起比较；未来起始按配置日期比较；不能据历史起始日不同直接判失败 |
| 预订规则名称 | 展示名称，不要求规则名称相同 |
| 预订规则细项 | 是否实名、验证信息、预订限制、性别、允许其他证件导入、生日等要求一致；不一致项标叉并阻止确认 |
| 年龄与区域 | 原文为“子票并集处理”，按主票优先、再其他子票，为游客逐个匹配；不能要求所有游客满足每一种子票条件 |
| 日历库存 | 校验子票库存大于0的日期集合一致；不是要求每天库存数值相等 |
| 总库存为0 | 校验页提示无法售卖，可保存；上架需要完整校验，不能将可保存视为可售 |
| 上架校验 | 重新检查规则、模式、日期、日历/总库存；子票售卖交集发生变化时需重新编辑套票 |

专项原文提示包括：“预订规则不一致，请检查子票配置”“日历库存不一致，请检查子票配置”“套票库存按最小子票库存售卖，有子票库存为0，建议配置，否则无法售卖”“校验不通过，请检查子票重新调整后再提交”。这些是历史方案提示，当前QA具体提示需实际截图核对。

## 三、实名与游客分配

| 套票实名模式 | 子票配置及下单规则 |
|---|---|
| 无需实名 | 子票应符合非实名要求；接口仍可传游客，优先分配给主票对应子票，不代表自动获得多人出票能力 |
| 需提供一位取票人身份信息 | 至少一个组合票实名；下单无游客信息报错，有一位或多位则按分配规则处理。V2.10.1补充：主票不能匹配时可尝试其他子票 |
| 所有游客需填写身份信息 | 所有子组合票实名；游客信息人数需与所需子票数量一致，否则游客信息验证失败。双人报名传2人应对应2张子票 |

游客验证还受证件类型、性别、年龄、生日、区域、限购/验重等子票规则约束。报名表允许填写2人，并不证明票务系统会接受2人。

## 四、价格、库存与日期

- 套票售价＝各子组合票单价×配置数量后求和。日历票按游玩日分别求和；票面价、渠道价、售卖价不得混淆。
- 套票可售份数按各子票库存除以该子票配置数量后的最小值计算。余数不足一套不能销售，整数取整展示需当前系统核实。
- 例：组合票库存100，套票包含该组合票×2，则最多50套；若需要100人名额，对应50套、消耗100张子组合票。
- 日历库存同样按每个游玩日进行数量折算，再取最小值。
- 套票可售日期取子组合票售卖日期交集；项目可报名时间再与所关联产品可售时间相交。比赛日/游玩日价格库存与购买时段是两个维度。
- 总库存模式有“统一调整子票售卖日期”选项：选是可能覆盖所有子票及套票日期，测试时应避免不知情修改共用子票。
- 固定使用有效期、日历游玩日还需覆盖赛事比赛日期；不能只看销售日期。

## 五、渠道授权与全域关联

1. 创建并保存符合规则的套票，配置线上预订销售渠道并上架。
2. 分销商管理找到“官网小程序”，通过“套票管理”授权该套票。此前在“产品管理”授权组合票不能代替这一步。
3. 在全域关联该真实套票产品，门票编码必须与票务系统套票编码对应；不能继续使用原子组合票编码。
4. 全域设置每券需要2位游客，报名项目单次2人，关联票购买数量为1套；三处人数含义同时匹配。
5. 全域原套票方案限制一次下单1张套票；不能用购买2张单人组合票替代报名固定买1张的链路。
6. 保存后重新打开两端，核对产品类型、编码、套票子票数量、主票、实名要求、价格和库存，再下单。

## 六、下单、拆单、发码与信息展示

- 下单接口识别套票类型，校验套票及子票规则，再自动拆分成对应数量子票。
- 每套生成一个主核销码，关联各子票券码；接口向全域返回套票主核销码。
- 双人全实名应形成1套、2张子票、各自绑定对应游客。全域可能展示1个码并列出2人，不能据一个码判为只有一位游客。
- 子券码格式以实际为准；原文包含不同示例与待确认分隔符，不将原型字符串当作当前接口约定。
- 全域按提交人数透传游玩人信息；原方案通过主码关联子码游客信息展示多人，需核对订单详情和实际子票记录。
- 未支付、已支付、发码成功是不同阶段；套票保存成功和可关联不代表完整链路已通过。

## 七、核销、窗口补录与查询

- 身份证或子票纸质码按相应子票核销；主电子码按套票规则检票，受各子票待确认/待使用状态约束。
- 任一子票检票后，联动主票使用状态并推送线上；不得出现子票已用而主票仍可按未用退款的漏洞。
- 配置“有证件免窗口确认，无证件需窗口确认”时，有证件子票待使用、缺证件子票待确认；自动与非自动检票的可检范围不同。
- 取票/线上票确认页可为允许状态下缺证件子票补录，按订单快照做预订规则与验重校验；V2.11.1明确符合状态的线下补录证件可修改，不能任意覆盖线上提交信息。
- 主码、子码、订单应可互查；订单及门票显示套票标识，能查看所属套票名称编码。
- V2.13.1修复主电子码检票时缆车接口漏推子票的问题，需推送所有已检子组合票。
- 窗口允许套票与其他组合票同单，但子组合票重复选择有限制；窗口数量上限与报名单次10人上限是两套约束。

## 八、退款、短信、统计和状态联动

| 环节 | 资料规则及边界 |
|---|---|
| 线上未检退票 | 专项方案要求套票所有子票整套退；概述含待开发标记，需实际验证实现，不能仅凭原文断言已强制实现 |
| 任一子票已检 | 线上按已使用控制；线下整套强退存在“人为控制、系统不控”描述，不能写作系统必然强制全部退 |
| 库存与报名人数 | 退款释放的是套票/子票库存，报名人数还依赖赛事退款结果处理，二者都要回查 |
| 票务短信 | V2.10.1只按主票产品模板发，子票不分别发；主票无模板不发；支持套票名称、价格、数量、主票号变量 |
| 赛事短信 | 赛事报名成功按参赛者发送是另一个功能，不能与票务主票短信规则混用，需关注是否重复通知 |
| 报表 | 带套票名称编码分类；套票检票分成联动及子票数量与整套数分别核对，不能将1套误计为1位游客 |
| 手动编辑/下架 | 引用已上架套票的子组合票变更规则、模式、日期或下架/删除受限制，应先处理对应套票 |
| 到期自动下架 | V2.19：到期组合票可级联下架引用它的套票；套票到期下架不下架子组合票；开关、执行与渠道同步仍需当前环境取证 |
| 导出 | V2.17补充套票非日历票票面价、渠道销售价、售卖单价（结算价）列 |
